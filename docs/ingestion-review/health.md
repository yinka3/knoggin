# Health layer scan

> Current verification (2026-10-19): see [verification status](verification-status.md) for the passing PostgreSQL runs, remaining coverage limits, and planned full Docling ingestion on Linux. Older database-unavailable statements below describe earlier runs.

Working notebook, 2026-10-08. Source code and actual test assertions are the authority here; the README may be stale. This is a read-only scan. “Healthy” below means the health service's status, not proof that extracted knowledge is correct.

## Boundaries and flow

- `ApplicationRuntime` creates one `RuntimeHealthService` and attaches it to sessions (`server/src/runtime/application.py:71-101`). It marks health as closing before shutdown (`server/src/runtime/application.py:192-203`). The health service does not own or mutate work (`server/src/core/health/service.py:1-20`).
- Four HTTP reads expose engine, resources, ingestion, and background snapshots (`server/src/api/app.py:501-531`). The API port checks the configured user and durable project existence before project reads (`server/src/runtime/api_port.py:138-177`); `get_project` is a metadata query, not a runtime load (`server/src/core/project/project_manager.py:383-402`). The agent has matching read-only tools and returns a degraded envelope on adapter errors (`server/src/core/agent/tools/health.py:31-108`). Tool definitions allow one call by default (`server/src/core/agent/tools/registry.py:162-182`).
- The common `HealthSnapshot` separates severity (`healthy`, `degraded`, `failed`) from activity (`idle`, `busy`, `delayed`), bounds output, and filters sensitive keys/obvious credential strings (`server/src/common/schema/health.py:24-37,40-105,109-173,176-214`). Internal synchronous snapshots are projected into this shape; durable reads and the PostgreSQL probe use a per-read timeout of 0.75 seconds by default (`server/src/core/health/service.py:29-32,678-691,738-751,773-799`).
- Engine health probes PostgreSQL with `SELECT 1` and checks that coordinator, store, executor, embedding, and hosted LLM *objects exist*. It also reads the pending global-merge projection repair count (`server/src/core/health/service.py:49-141,718-756`). Startup loads the local embedder/reranker, English VP-01, spaCy tokenizer, and LLM tokenizer before resources become ready; multilingual VP-01 and Docling PDF models can load later (`server/src/runtime/resources.py:95-142,144-176,295-333`; `server/src/core/knowledge/documents/extraction.py:384-440`). Engine health never runs a hosted LLM/JEV request or local embedder/VP-01/Docling inference, and JEV/VP-01/Docling are absent from its dependency list (`server/src/core/health/service.py:56-68`). Resource health reports shared model-work queue and capacity, not individual model availability or output quality (`server/src/core/health/service.py:150-236,801-843`). A green model-related result can claim successful startup and current object/queue state, not that a model call would succeed now.
- Ingestion health reads the project semantic scheduler, durable semantic-window counts, and Context file-projection state (`server/src/core/health/service.py:238-394,570-676`). A semantic window is a single active project checkpoint through Episode, Context, Knowledge, and completion (`server/src/core/ingestion/project_semantic_processor.py:138-149`; `server/src/infrastructure/schema.sql:810,1295`). The durable summary counts noncompleted, claimed, failed, and exhausted windows and computes age from `claimed_at` (`server/src/core/knowledge/db/readers/semantic_window_reader.py:255-296`). A completed window is not counted as pending.
- Background health combines scheduler outcome/activity, project background queue, indexing task snapshot, and durable retryable document count; assisted conflict discovery is checked only when configured (`server/src/core/health/service.py:396-545`). The document indexer's pending count comes from `DocumentReader.count_documents_for_index_recovery()` (`server/src/core/knowledge/documents/indexer.py:555-575`; `server/src/core/knowledge/db/readers/document_reader.py:347-360`).

## Rules and opinions visible in code

- Health favors small, redacted diagnostics: counts and categories rather than message, Context, document, or exception contents. Projection failure exposes exception *type* and age, but not the stored summary (`server/src/core/knowledge/context/projection.py:446-463`; `server/src/core/health/service.py:659-675`; `server/tests/unit/health/test_runtime_health_service.py:406-453`).
- A missing project runtime is degraded rather than failed, while a missing core runtime dependency makes engine health failed (`server/src/core/health/service.py:85-96,308-328,475-504`). Queue pressure can make resource health degraded without a job failure (`server/src/core/health/service.py:171-224`).
- Semantic-window failures and exhausted retries degrade ingestion health; a pending window with a running scheduler is reported as busy and “delay unknown,” regardless of its age (`server/src/core/health/service.py:280-339`). This encodes a cautious refusal to claim an SLA from age, but the top-level status still says healthy.
- Health is an execution and availability view. It does not count extraction `ValidationIssue`s, unsupported associations, or whether Context/Knowledge assertions are semantically right. The source-only entity issue sits in the in-memory semantic build, so health cannot report that omission after the window completes (`server/src/core/ingestion/batch.py:26-44`; `server/src/core/health/service.py:238-394`). This is a scope limit, not evidence that those decisions succeeded.

## Defects and cascading paths

1. **Terminal document-index failures disappear from background health.** `record_index_failure` leaves a nonretryable/exhausted document at `status='failed'` with `next_index_retry_at=NULL` (`server/src/core/knowledge/db/writers/document_writer.py:588-619,628-640`). The health count includes only `queued` and `failed` rows with a nonnull retry time (`server/src/core/knowledge/db/readers/document_reader.py:347-360`). The local indexing snapshot has task/recovery counts, not terminal-failure count (`server/src/core/knowledge/documents/indexer.py:558-575`). An index task failure is logged (`server/src/core/knowledge/documents/indexer.py:389-403`), while background health ignores the coordinator's failure total (`server/src/infrastructure/background_work.py:259-275`; `server/src/core/health/service.py:433-504`). It can therefore show healthy as soon as active work clears. A new document has no current snapshot and is absent from retrieval; a failed update can still expose the prior snapshot (`server/src/core/knowledge/db/writers/document_writer.py:588-590`; `server/src/core/knowledge/db/readers/document_reader.py:449-480`). This is a health-to-knowledge blind spot. Preserve a scoped terminal-failure count and surface it separately from retryable work.
2. **Old semantic windows can stay green indefinitely.** The durable query supplies the age of the oldest noncompleted window (`server/src/core/knowledge/db/readers/semantic_window_reader.py:269-280`), and health computes that age but never uses it for status or delay (`server/src/core/health/service.py:280-328,612-628`). If a window stops making progress while the scheduler still reports `running` and no failure is recorded, ingestion health says healthy/busy. This can hide an Episode → Context → Knowledge blockage and hold the project's one-active-window slot (`server/src/infrastructure/schema.sql:1295`). The existing unit test sets `oldest_pending_ms=1` (an extremely old timestamp) and *expects* healthy (`server/tests/unit/health/test_runtime_health_service.py:289-323`). A stage-aware freshness rule or a clear `unknown` top-level status needs design; current status overstates confidence.
3. **Background health mistakes unrelated work for document-index progress.** Its “not progressing” condition requires *all* scheduler and background work to be absent (`server/src/core/health/service.py:493-501`). A running `project_semantic` or conflict-discovery job, or unrelated background task, can keep it healthy while documents remain pending and the index admission loop has died. The scheduler snapshot already exposes job names/states (`server/src/infrastructure/job/scheduler.py:403-480`); the indexer exposes `admission_loop_active` (`server/src/core/knowledge/documents/indexer.py:558-574`). Health should associate pending documents with actual indexing activity and retry timing.
4. **Scheduler admission failures are invisible to ingestion status.** `_check_jobs()` catches `should_run`/admission-check exceptions and only logs them (`server/src/infrastructure/job/scheduler.py:194-204,223-263`). Its `recent_failed_jobs` counts only outcomes of jobs that were admitted (`server/src/infrastructure/job/scheduler.py:475-480`). Ingestion health checks scheduler `running` and that recent outcome count (`server/src/core/health/service.py:275-328`), so repeated semantic admission errors can be hidden when the separate health query succeeds. This combines with the missing pending-age rule above. Record bounded per-job check failure counts or last check status and include the semantic job's state.
5. **A failed maintenance-health read still allows green engine health.** `_read_maintenance_projection_repair` returns `available=False, pending_count=0` when the service is missing or its read fails (`server/src/core/health/service.py:123-141`). Engine severity and warnings inspect only `pending_count`, not `available` (`server/src/core/health/service.py:72-96`). A pending global-entity merge projection repair can therefore be unknown while the engine claims healthy. The unit “healthy” fixture omits maintenance service entirely, so this behavior is expected by that test (`server/tests/unit/health/test_runtime_health_service.py:166-187`). Degrade or clearly mark this check unavailable when it is expected.

## Coverage read

- Unit tests verify typed/redacted snapshots, PostgreSQL failure handling, queued/exhausted window representation, stopped scheduler, model pressure, and assisted conflict-discovery availability (`server/tests/unit/common/test_health.py`; `server/tests/unit/health/test_runtime_health_service.py:166-213,259-284,327-453,490-666`). These are useful contract checks, mostly with synthetic snapshots.
- `test_health_drilldown_flow.py` has an integration marker but uses fake PostgreSQL, fake coordinators, and a fake project. It verifies bounded/scoped/read-only adapter output, not real queue transitions or scheduler liveness (`server/tests/integration/test_health_drilldown_flow.py:10-126`). API contract tests check route delegation and response shape with a fake port (`server/tests/contract/api/test_app.py:380-408`).
- A real-Postgres contract asserts the semantic-window summary after failure and manual retry (`server/tests/contract/storage/test_project_context_window_contract.py:953-982`), and document-service tests show terminal parse failure and transient retry (`server/tests/unit/core/knowledge/test_document_service.py:2605-2673`). None links these producer states through `RuntimeHealthService` to its final status. Scheduler health tests cover stalled active runs and bounded recent outcomes, not `should_run` check failures (`server/tests/unit/health/test_scheduler_health.py:26-68`).
- Meaningful missing cases: terminal failed document with no retry; pending indexing plus unrelated active work; an old claimed semantic window and a failed scheduler check; unavailable maintenance repair metric; live producer → health status after durable state transitions. These target the false-green paths above rather than mirroring implementation details.

## Follow-up questions

- What age or stage-specific progress threshold should mark a semantic window delayed? The processor cadence is 30 seconds, but Context and model work can legitimately take longer (`server/src/core/ingestion/project_semantic_processor.py:138-149`). A threshold needs observed runtime durations, not an arbitrary constant.
- Should health report terminal document failures as degraded indefinitely until explicit retry/removal, even when an older published snapshot remains searchable? The writer deliberately retains older snapshots on failed updates (`server/src/core/knowledge/db/writers/document_writer.py:588-590`).
