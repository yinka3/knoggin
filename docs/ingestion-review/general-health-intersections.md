# General ingestion and health intersections

Code-backed working notes, 2026-10-08. This pass reads the current worktree and the tests' actual assertions; it does not treat a passing test as proof of an untested boundary. No production code was changed in this pass.

## Boundary map

1. A session seals and closes an exchange, then sends an in-memory wake hint to the project scheduler (`server/src/runtime/session_runtime.py:925-960`, `server/src/runtime/project_runtime.py:80-86`). The scheduler also polls every 30 seconds (`server/src/infrastructure/job/scheduler.py:29, 207-219`).
2. The project semantic job selects eligible, unclaimed exchanges, claims a durable window, and advances Episode, Context, Knowledge, and finalization checkpoints (`server/src/core/ingestion/semantic_window_admission.py:119-225`, `server/src/core/ingestion/project_semantic_processor.py:228-346`). Knowledge extraction runs only after Context is committed (`server/src/core/ingestion/project_semantic_processor.py:617-685`).
3. Ingestion health combines an in-memory scheduler snapshot with a SQL aggregate over **already claimed windows** and a Context projection diagnostic (`server/src/core/health/service.py:238-276, 570-674`; `server/src/core/knowledge/db/readers/semantic_window_reader.py:255-300`). Global entity maintenance uses a separate SQL quiescence read that also counts closed, unclaimed exchanges (`server/src/core/knowledge/db/readers/semantic_window_reader.py:512-587`).
4. Document indexing is a parallel ingestion route. Search sees chunks from the current document snapshot; background health reads the count of documents eligible for automatic index recovery (`server/src/core/knowledge/db/readers/document_reader.py:347-360, 475-481`; `server/src/core/health/service.py:433-453`).

## Findings

### 1. Failed or cancelled exchanges can indefinitely block global entity maintenance — high

The message writer allows and seals `failed` and `cancelled` exchanges (`server/src/core/knowledge/db/writers/message_lifecycle_writer.py:224-240, 333-338`). Semantic admission intentionally skips them, so they never receive window membership (`server/src/core/ingestion/semantic_window_admission.py:267-276`). But maintenance quiescence counts every closed, unclaimed eligible exchange without filtering those outcomes (`server/src/core/knowledge/db/readers/semantic_window_reader.py:530-542`). `capture_frontier()` rejects any positive count; revalidation does too (`server/src/core/knowledge/entity/maintenance_service.py:682-703, 744-755`). One ordinary failed or cancelled agent turn can therefore leave global entity maintenance unable to capture a stable frontier for that project even after all real semantic work completes. Ingestion health may show no pending window because no window was claimed for that exchange (finding 3).

**Recommendation:** Make quiescence pending work match admission's eligible outcomes. Keep `failed`/`cancelled` out of semantic evidence, and decide separately whether their message IDs should still advance the freshness token. Add a real Postgres contract with a closed failed exchange, a closed cancelled exchange, and a later successful exchange: admission skips the first two, the successful one completes, and frontier capture succeeds. Also assert a valid closed unclaimed exchange still blocks maintenance.

### 2. Scheduler timeouts do not consume the semantic window's durable retry budget — high

The scheduler cancels job execution through `asyncio.timeout` and records `timed_out` only in its local recent-outcomes list (`server/src/infrastructure/job/scheduler.py:312-345, 376-401`). The semantic stages record durable failure only inside `except Exception` handlers; timeout cancellation bypasses them (`server/src/core/ingestion/project_semantic_processor.py:440-451, 573-584, 687-699, 752-763`). `_record_failure()` is what increments the window's attempt count and schedules backoff or exhaustion (`server/src/core/ingestion/project_semantic_processor.py:800-830`; `server/src/core/knowledge/db/writers/semantic_window_writer.py:248-277`). A stage that times out repeatedly can remain due without consuming those attempts. Restarting the runtime also loses the scheduler's local outcomes, so health can lose the only timeout signal while extraction and Knowledge remain behind that window.

**Recommendation:** Give scheduler timeouts a stage-aware, durable failure path after the cancelled operation has unwound. Guard it with the expected window ID and stage so a completed checkpoint cannot be marked failed, and keep normal shutdown cancellation distinct. Test a timed-out semantic stage through the scheduler, then restart the scheduler and verify attempt count, backoff, eventual exhaustion, and ingestion-health status from the durable row. The current scheduler timeout test checks emitted local events only (`server/tests/unit/runtime/test_scheduler_contract.py:199-208`).

### 3. Ingestion health cannot see unclaimed exchange backlog or FIFO barriers — medium

Admission reads unclaimed messages and can defer a session when its next exchange is not safely sealed or has invalid terminal structure; later exchanges in that session remain behind it (`server/src/core/ingestion/semantic_window_admission.py:119-126, 230-280`). Health's SQL source counts only rows in `project_semantic_windows`, so an unclaimed backlog has `pending_count=0`; with a running scheduler and no failed job, the endpoint can report `healthy` and `idle` (`server/src/core/knowledge/db/readers/semantic_window_reader.py:255-284`; `server/src/core/health/service.py:271-327, 330-349`). The maintenance quiescence reader already proves that closed unclaimed exchanges matter, although its count needs the correction in finding 1. This can hide a delay before Episode, Context, extraction, and Knowledge ever start.

**Recommendation:** Add a bounded, payload-free admission read for closed unclaimed exchanges, the oldest *due* head, and blocked session heads by reason. Apply the expected five-minute idle flush and 30-second scheduler cadence before calling ordinary waiting work late (`server/src/core/ingestion/semantic_window_admission.py:69, 140-149`; `server/src/infrastructure/job/scheduler.py:29`). Test a real closed exchange with no claimed window, plus a malformed FIFO head followed by a valid exchange. A pure fake-window health test cannot cover this boundary.

### 4. Terminal document-index failures disappear from background health — medium

An invalid-content error or exhausted retry leaves a document `failed` with `next_index_retry_at = NULL` (`server/src/core/knowledge/db/writers/document_writer.py:608-654`; `server/tests/unit/core/knowledge/test_document_service.py:2607-2632`). The count used by background health includes `queued` and retryable `failed` rows only (`server/src/core/knowledge/db/readers/document_reader.py:347-360`; `server/src/core/knowledge/documents/indexer.py:555-556`; `server/src/core/health/service.py:433-453`). Document indexing runs through the indexer's own admission loop or background coordinator, not a registered scheduler job (`server/src/core/knowledge/documents/indexer.py:335-357,408-467`; `server/src/runtime/project_factory.py:338-380`). Health does not inspect the background coordinator's failure total, so it can report healthy once active work clears and the pending count returns zero (`server/src/infrastructure/background_work.py:244-275`; `server/src/core/health/service.py:433-504`). For a new document, or a changed document whose current snapshot was cleared, search has no current chunks to return (`server/src/core/knowledge/db/writers/document_writer.py:157-182`; `server/src/core/knowledge/db/readers/document_reader.py:475-481`).

**Recommendation:** Report terminal failed document count separately from retryable backlog and degrade background health while one is present. Keep error text out of the public health payload; a bounded failure kind is enough. Join a real terminal-failure row to the health read in a storage-backed test, and verify that its absent search result is visible as an indexing problem. The existing document test proves no retry is scheduled, but does not check health.

### 5. Scheduler preflight failures are logged but absent from health — medium

`ProjectSemanticProcessor.should_run()` reads the active durable window (`server/src/core/ingestion/project_semantic_processor.py:211-224`). If `job.should_run()` raises during scheduler preflight, `_check_jobs()` logs and continues without creating a run or recording an outcome (`server/src/infrastructure/job/scheduler.py:194-204, 229-252`). The scheduler health snapshot counts only outcomes recorded by `_finish_job_run()` after execution begins (`server/src/infrastructure/job/scheduler.py:376-401, 403-480`). If the window aggregate query still succeeds, ingestion health can say healthy even though the job cannot be scheduled (`server/src/core/health/service.py:271-327`). One example is an active-window row that fails model validation while the aggregate SQL still returns normally.

**Recommendation:** Record a bounded scheduler check-failure signal by job, with no exception text in the health payload, and let ingestion health degrade when its semantic job repeatedly fails checks. Test a `should_run()` exception through `_check_jobs()` and assert the health snapshot changes, then assert a later good check clears or ages out the signal.

### 6. Claimed-window age is displayed but never used to detect delay — lower

The window reader returns the oldest active claim timestamp and health converts it to seconds (`server/src/core/knowledge/db/readers/semantic_window_reader.py:267-280`; `server/src/core/health/service.py:612-627`). Health sets `delay_state = "unknown"` for every pending window unless the scheduler is stopped or currently stalled, and can still report healthy (`server/src/core/health/service.py:280-327`). A unit test deliberately supplies `oldest_pending_ms=1` and asserts `healthy` (`server/tests/unit/health/test_runtime_health_service.py:289-323`). That test verifies the current response shape, not progress. A due window with no active run can remain old without an ingestion-health warning.

**Recommendation:** Base delay on whether the window's next stage is actually due, its retry time, the scheduler cadence, and last progress time. Do not use age alone: a legitimate backoff or a long running stage needs different handling. Add a case where a due window stays unprocessed past a defined grace period, plus a case in valid backoff.

### 7. Admission work grows with all retained exchanges and repeatedly tokenizes the selected prefix — medium

Despite its name, `get_unclaimed_project_semantic_exchange_rows()` returns every participation-eligible exchange in each open session, including rows already claimed in older windows, with no SQL limit (`server/src/core/knowledge/db/readers/semantic_window_reader.py:465-509`). Admission fetches all those contents every time it selects and discards claimed rows in Python (`server/src/core/ingestion/semantic_window_admission.py:119-124, 230-242`). For the remaining exchanges, it renders and tokenizes the whole growing prefix after each appended exchange (`server/src/core/ingestion/semantic_window_admission.py:130-145, 314-326`). With many small exchanges below the window target, this repeats earlier text and can approach quadratic tokenization work. The 30-second scheduler cadence repeats the scan (`server/src/infrastructure/job/scheduler.py:29, 207-219`). As a project grows, admission may delay claims, monopolize the event loop during tokenization, or reach the job timeout in finding 2 before extraction and Knowledge begin. Ingestion health does not observe the unclaimed backlog (finding 3).

**Recommendation:** Move already-claimed exclusion into the bounded database read while preserving per-session FIFO blockers, and avoid retokenizing the entire selected prefix for each exchange. Verify exact window membership and token counts remain unchanged. Add a scaling test or benchmark that increases historical claimed exchanges independently from current pending exchanges, then many small pending exchanges; assert read volume and token-counter work stay bounded by the relevant pending prefix.

### 8. Concurrent document uploads can leave a catalog row without its source file — high

Upload writes source bytes before inserting a catalog row; an insert failure deletes those bytes if their hash still matches (`server/src/core/knowledge/documents/service.py:1091-1118`). The create-only filesystem write checks existence before an unconditional `os.replace`, so two same-path uploads can both pass and publish file bytes (`server/src/core/knowledge/documents/filesystem.py:94-151`). PostgreSQL permits only one live document row per project path (`server/src/infrastructure/schema.sql:1301`). A controlled local run of two real `DocumentService.add_document()` calls with a fake unique-path writer produced one accepted row, one duplicate-path error, and no source file: the losing call's cleanup removed the accepted call's bytes. The indexer may then fail to read the accepted document, and the terminal-failure health gap in finding 4 can hide that later state (`server/src/core/knowledge/documents/indexer.py:103-182`; `server/src/core/health/service.py:433-504`). The local reproduction establishes the interleaving and cleanup behavior; a real Postgres concurrency contract remains to be run.

**Recommendation:** Make create-only publication atomic with respect to other writers of the same path, and couple duplicate-path cleanup to ownership of the bytes it created. In a Postgres-backed concurrent upload test, assert one accepted row retains readable bytes with its catalog hash, both immediately and after indexing/reconciliation. The existing filesystem test checks only sequential create/replace behavior, and the catalog-failure test has one upload (`server/tests/unit/core/knowledge/test_project_filesystem.py:32-49`; `server/tests/unit/core/knowledge/test_document_service.py:1127-1137`).

### 9. Cancelled document uploads can reappear through reconciliation — medium

`DocumentService.add_document()` writes source bytes before inserting a catalog row, and its cleanup catches `Exception` but not `asyncio.CancelledError` (`server/src/core/knowledge/documents/service.py:1091-1118`). A local call with cancellation during the insert left the source file with no catalog row. Periodic project-file reconciliation can then discover and catalog that orphan as a new document (`server/src/core/knowledge/documents/service.py:164-181,329-395`; `server/src/core/knowledge/documents/indexer.py:480-509`). This crosses from a cancelled API operation into later document Knowledge. The unit test for a failed insert uses `RuntimeError`, while the source-batch cancellation test uses a fake service and never checks project files (`server/tests/unit/core/knowledge/test_document_service.py:1127-1137`; `server/tests/unit/api/test_source_batches.py:52-58`).

**Recommendation:** Ensure the file/catalog boundary completes or cleans up under cancellation, including cancellation of the worker thread before it returns. Test that a cancelled upload leaves no catalog row or source file and that a later reconciliation does not index it.

### 10. Missing PDF parser models become terminal document failures — medium

Docling's local PDF converter now raises `DependencyError` with setup guidance when model artifacts are missing, so the indexer classifies this as retryable `transient_dependency` (`server/src/core/knowledge/documents/extraction.py`; `server/src/core/knowledge/documents/indexer.py`). Bounded retries can still exhaust before artifacts are installed, leaving a terminal failure that background health misses (finding 4). Model health does not probe Docling, and the cached-model smoke lane does not convert a PDF (`server/src/core/health/service.py:56-68,433-504`; `.github/workflows/server-tests.yml:219-288`).

**Recommendation:** Show exhausted dependency failures in scoped health and run a real cached PDF conversion in the model lane. Define how failed documents are requeued after artifacts are provisioned; a focused test should verify that recovery path.

### 11. Inline indexing failure makes a saved upload look rejected — medium

`submit_document()` saves the source file and queued catalog row before scheduling its index (`server/src/core/knowledge/documents/service.py:1058-1134,1175-1192`). Small documents index inline, so a parser or embedding error propagates after that durable write (`server/src/core/knowledge/documents/indexer.py:315-345`). The single-upload API returns an error; the source-batch API emits `BatchSourceFailed` with no document ID (`server/src/runtime/api_port.py:592-649`). A local service repro with a failing indexer returned an error while one catalog row and its file remained. A same-path client retry then encounters the existing file. Terminal index failures can also be invisible in background health (finding 4). Current batch tests inject an `AsyncMock` service and never assert durable state after an indexing failure (`server/tests/unit/api/test_source_batches.py:16-48`).

**Recommendation:** After source admission succeeds, return the durable document identity and indexing state even if inline indexing fails, or define an idempotent upload retry that finds the saved row. Verify the public response, catalog row, file bytes, and subsequent retry in one test.

### 12. Windows project deletion leaves native files pending

`ProjectFilesystemFactory.remove_project_directory()` previously refused to remove a real project directory when `shutil.rmtree.avoids_symlink_attacks` was false. That flag is false in this Windows environment, so deletion left `file_cleanup_status='pending'` and retry/startup cleanup could not clear it. A Windows-specific walker now removes ordinary entries and removes symlinks and junctions without descending into them; the original guarded `rmtree` path remains for other platforms. After Windows Developer Mode was enabled on 2026-10-10, the combined filesystem and project-membership pytest suites passed all **37 tests**, including symlink and Windows junction coverage, using the installed system Python with packages from the repo virtual environment and the pytest-asyncio plugin. A direct Windows smoke check also confirmed that nested and root junction targets outside the project stayed intact. The Windows walker does not have the descriptor-based race protection of the POSIX `rmtree` implementation; a hostile process concurrently replacing directory entries is a remaining limitation.

## Coverage assessment

- Admission tests prove failed/cancelled exchanges are excluded from evidence (`server/tests/unit/core/ingestion/test_semantic_window_admission.py:137-154`). Maintenance tests supply a fabricated `pending_exchange_count` and prove a positive count blocks frontier capture (`server/tests/unit/knowledge/test_global_entity_maintenance_contract.py:100-136`). No test combines the actual admission outcome with the SQL quiescence count.
- Scheduler tests prove a timeout emits a local event (`server/tests/unit/runtime/test_scheduler_contract.py:199-208`). Semantic retry tests exercise normal `Exception` failures and durable backoff (`server/tests/unit/core/ingestion/test_semantic_window_admission.py:725-741, 785-791`). None drives a semantic stage through scheduler timeout and checks the durable row after restart.
- Health tests mostly inject fake queue and scheduler snapshots. The pending-window test even asserts `healthy` for a claim timestamp of 1 ms since epoch (`server/tests/unit/health/test_runtime_health_service.py:289-323`). They do not run admission, SQL health aggregation, and health evaluation together.
- The document test verifies a parser failure persists `failed`, has no retry time, and cannot be recovered automatically (`server/tests/unit/core/knowledge/test_document_service.py:2607-2632`). It does not query background health with that durable row.
- Admission unit tests use short synthetic row lists. They check selection rules but do not measure database rows fetched from a long history or repeated token-counter work (`server/tests/unit/core/ingestion/test_semantic_window_admission.py:25-108, 137-154`).

This review is static. The storage-backed boundary checks above remain to be implemented and run; existing Postgres-dependent ingestion contracts in the earlier review could not run against a local database.
