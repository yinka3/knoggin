# General ingestion scan

Working notes, 2026-10-08. This follows the live code and test assertions; the README is background only. The earlier [Extraction](extraction.md), [Knowledge](knowledge.md), and [handoff](intersection.md) notes cover the deeper semantic stages.

## Live path

1. A session accepts the user turn under a durable idempotency key. An editable message is not semantic evidence yet. The assistant-final path atomically writes the assistant message, source references, and terminal exchange; non-assistant paths close the user exchange. Both closure paths wake the project scheduler, while its poll recovers a missed local wake (`server/src/runtime/session_runtime.py:583-632,811-849,862-903,925-968`; `server/src/runtime/project_runtime.py:81-86`).
2. The project registers one `ProjectSemanticProcessor`. Its local scheduler checks every 30 seconds, queues the job through the shared bounded background coordinator, and gives the entire execution a 300-second timeout. A new window is found by cadence even though `should_run()` returns false when no window is active (`server/src/runtime/project_factory.py:258-314,360-370`; `server/src/infrastructure/job/scheduler.py:26-31,223-293,305-357`; `server/src/core/ingestion/project_semantic_processor.py:211-266`).
3. Admission reads eligible exchanges from open, participating sessions after each session's participation frontier. It keeps sealed, closed, whole exchanges, respects each session's FIFO barrier, skips failed/cancelled outcomes, and accepts assistant-final, clarification, and user-only outcomes. It closes when the rendered prefix crosses the configured token target, or after five idle minutes; an oversized exchange is kept whole. It records membership, domain, Episode rules, and ingestion policy in the window (`server/src/core/knowledge/db/readers/semantic_window_reader.py:35-69,462-509`; `server/src/core/ingestion/semantic_window_admission.py:101-203,230-323`). The SQL writer rechecks selected member eligibility under the project lock (`server/src/core/knowledge/db/writers/semantic_window_writer.py:57-146,400-489`).
4. One claimed window drains Episode, Context, Knowledge, then finalization. The processor reloads the durable row after each successful stage and stops if it did not advance. Episode and Context consume the frozen message membership; Context can also receive source references owned by included assistant messages. Knowledge reopens the exact committed Context revision and impact closure; finalization publishes resolver IDs and enriches Episodes (`server/src/core/ingestion/project_semantic_processor.py:268-346,380-450,452-583,617-762`; `server/src/core/knowledge/db/readers/semantic_window_reader.py:332-426`). Human Context edits enter as their own window at the Context checkpoint; see [handoff](intersection.md).
5. Document upload is a separate ingestion route. The API bounds and decodes the body; `DocumentService` writes source bytes to the project tree, inserts a queued catalog row, then indexes inline or admits background work. The indexer parses, chunks, embeds, and atomically publishes a current snapshot; search reads only current snapshots (`server/src/api/upload_limits.py:15-58`; `server/src/runtime/api_port.py:632-649`; `server/src/core/knowledge/documents/service.py:1058-1134,1175-1192`; `server/src/core/knowledge/documents/indexer.py:103-182`; `server/src/core/knowledge/db/readers/document_reader.py:449-481`).

## Models, limits, and design choices

| Work | Live choice and boundary |
| --- | --- |
| Admission size | `LLMService.count_tokens()` uses `cl100k_base`, with `len(text)//4` fallback; it is an estimate for the configured 128,000-token target, not a provider-specific Context limit (`server/src/infrastructure/llm_client.py:115-125,300-306`; `server/src/common/schema/settings.py:59-67`). |
| Episode and Context | Both call `generate_structured()` without a model override, so the configured hosted `extraction_model` is used. Episode output has local message-handle, non-overlap, source-count/token, and narrative limits; only valid episodes are embedded. Context output is validated against frozen message/source handles before a revision write (`server/src/core/knowledge/episodes/generator.py:102-141`; `server/src/core/knowledge/episodes/build.py:88-135`; `server/src/core/knowledge/context/updater.py:423-450`; `server/src/infrastructure/llm_client.py:519-545`). |
| Extraction and Knowledge | Local VP-01 and embedding/reranking work use bounded model workers; structured entity fallback and relationship extraction use the hosted extraction model. See [model routing](models-and-coverage.md) for details (`server/src/infrastructure/model_work.py:56-89`; `server/src/runtime/resources.py:200-224,261-289`). |
| Document parsing | PDF and DOCX use a lazy, serialized local Docling converter; images use Tesseract; code/structured text use local parsers. The Docling PDF pipeline enables layout, tables, and OCR but disables remote services (`server/src/core/knowledge/documents/extraction.py:344-440,707-743`). The ordinary model smoke lane does not run a real Docling conversion (`.github/workflows/server-tests.yml:219-288`). |
| External spend | The LLM service reserves against a server-wide ledger before each structured provider attempt; validation retries each get a reservation. The configured limit is optional and defaults to no cap. JEV shares this ledger when enabled (`server/src/infrastructure/llm_client.py:50-76,519-651`; `server/src/infrastructure/external_model_budget.py:36-55,79-140`; `server/src/common/schema/settings.py:145-176`; `server/src/runtime/resources.py:261-279`). |

The code favors durable source membership, stage-local checkpoints, and conservative evidence boundaries. A successful stage resets its retry count; a caught stage exception increments the durable count and applies exponential backoff, capped at three attempts by default (`server/src/core/knowledge/db/writers/semantic_window_writer.py:174-212,216-281`; `server/src/core/ingestion/project_semantic_processor.py:585-615,800-830`; `server/src/common/schema/settings.py:45-66`). Domain, Episode, and ingestion rules are frozen, but the provider model name comes from the live LLM service. A config change before a stage retry can therefore change which model performs that stage; this is a replay-consistency tradeoff, not an observed corruption (`server/src/core/ingestion/semantic_window_admission.py:168-198`; `server/src/infrastructure/llm_client.py:215-263,519-533`).

## Defects and cascading paths

1. **Failed/cancelled exchanges can permanently block global entity merge work.** Admission deliberately skips these terminal outcomes and never claims their messages (`server/src/core/ingestion/semantic_window_admission.py:262-285`). The maintenance frontier nevertheless counts *every* unclaimed closed eligible exchange as pending, without excluding those outcomes (`server/src/core/knowledge/db/readers/semantic_window_reader.py:530-542`). `capture_frontier()` then rejects the project, and `revalidate_frontier()` also fails (`server/src/core/knowledge/entity/maintenance_service.py:668-702,732-755`). A normal failed or cancelled agent run can thus prevent merge previews, reviews, and execution for that project until participation/session state changes (`server/src/core/knowledge/entity/maintenance_service.py:129-138,194-198,234-255,363-372`). The unit admission test verifies exclusion, and the maintenance unit test injects `pending_exchange_count=1`, but no test joins those rules with a real failed/cancelled exchange (`server/tests/unit/core/ingestion/test_semantic_window_admission.py:135-153`; `server/tests/unit/knowledge/test_global_entity_maintenance_contract.py:130-148`). Repair the quiescence predicate to match admission's participation and outcome rules, then add a Postgres contract that closes failed/cancelled exchanges and proves the frontier becomes available.
2. **The scheduler timeout bypasses durable retry accounting.** A 300-second `asyncio.timeout()` covers the whole multi-stage job and records only a local `timed_out` job outcome (`server/src/infrastructure/job/scheduler.py:29-31,305-357`). The stage handlers catch `Exception` and call `_record_failure`, but timeout cancellation does not enter those handlers (`server/src/core/ingestion/project_semantic_processor.py:380-450,689-697,699-762,800-830`). The window remains at its last checkpoint with unchanged `attempt_count` and `next_retry_at_ms`; the next poll can repeat the expensive model work without backoff or an exhaustion state. This can keep later windows behind the active one and underreport a persistent failure in durable semantic health. The scheduler test asserts only local timeout/cancelled events, while stage retry tests inject regular exceptions (`server/tests/unit/runtime/test_scheduler_contract.py:197-219`; `server/tests/unit/core/ingestion/test_semantic_window_admission.py:628-678`). Add a timeout-aware durable failure path and a test that runs the semantic job through the scheduler, then asserts the persisted retry state.
3. **Admission cost grows with history and with a large pending prefix.** The reader fetches all eligible project exchanges, including previously claimed ones, on every cadence check; Python discards claimed rows afterward (`server/src/core/knowledge/db/readers/semantic_window_reader.py:462-509`; `server/src/core/ingestion/semantic_window_admission.py:230-259`). So even an idle long-lived project pays a growing SQL/transfer scan. For exchanges considered before crossing the current window target, admission rerenders and retokenizes the full growing prefix at each step, making that part quadratic in the number of exchanges considered (`server/src/core/ingestion/semantic_window_admission.py:127-151,314-323`). This is a throughput/timeout risk rather than a demonstrated wrong result. Bound the SQL to unclaimed work plus the FIFO barriers it needs, and benchmark many short exchanges before choosing a token-count optimization.
4. **Concurrent same-path uploads can remove the accepted document's file.** `ProjectFilesystem.write_bytes(overwrite=False)` checks `path.exists()` before creating a temporary file, then uses `os.replace`, which can replace a file another upload created after that check (`server/src/core/knowledge/documents/filesystem.py:94-151`). The live API routes uploads through `asyncio.to_thread` without a path lock (`server/src/runtime/project_factory.py:193-242`; `server/src/runtime/api_port.py:632-649`). The catalog has one-live-document-per-path uniqueness (`server/src/infrastructure/schema.sql:1301`). If both file writes succeed, one catalog insert loses; its failure cleanup deletes the file when its hash matches, potentially removing the file expected by the winning catalog row (`server/src/core/knowledge/documents/service.py:1091-1118`). A controlled local repro ran two real `DocumentService.add_document()` calls with the same bytes, pausing both filesystem writes after the existence check and using a fake writer that enforces the catalog's unique-path rule. **One upload was accepted, one got a duplicate-path error, one catalog row remained, and its source file was gone.** The same-path interleaving is proven locally; the SQL transaction behavior still needs a real Postgres contract. Use an atomic no-replace create or a shared per-path transaction protocol, then assert that two concurrent uploads leave one catalog row and its exact file bytes intact.
5. **Cancelling upload during catalog insertion leaves an orphan source file.** `add_document()` writes the file first, then catches `Exception` around its catalog insert to remove the file on failure (`server/src/core/knowledge/documents/service.py:1091-1118`). `asyncio.CancelledError` bypasses that handler. An isolated call with a cancelled writer left the file present and no catalog row. The periodic reconciliation path catalogs local files that match the folder policy, so a later run can ingest that cancelled upload as a project file (`server/src/core/knowledge/documents/service.py:164-181,329-395`; `server/src/core/knowledge/documents/indexer.py:480-509`). Cancellation while the `asyncio.to_thread` file write is still running can create a similar orphan because the worker may finish after the coroutine stops; that timing has not been reproduced here. Make file publication and catalog insertion cancellation-safe, and assert no orphan or unintended later indexing after cancellation.
6. **Missing Docling artifacts now use dependency retry classification.** The local PDF converter raises `DependencyError` with setup guidance for missing artifacts, and the indexer records retryable `transient_dependency`. The parser regression checks this boundary (`server/src/core/knowledge/documents/extraction.py`; `server/tests/unit/core/knowledge/test_document_extraction_contract.py`). Retries are bounded by the document policy, so a PDF exhausted before provisioning still needs explicit reindex. The model smoke lane omits a real PDF parse; artifact availability remains unverified there.
7. **Inline indexing can return an upload error after the source was saved.** `submit_document()` first persists file bytes and a queued catalog row, then awaits indexing (`server/src/core/knowledge/documents/service.py:1058-1134,1175-1192`). Small documents index inline and propagate an index error (`server/src/core/knowledge/documents/indexer.py:315-345`). The single upload endpoint returns an error, and the batch endpoint records `BatchSourceFailed` without the persisted document ID (`server/src/runtime/api_port.py:592-649`). An isolated call with a failing indexer left one catalog row and file while `submit_document()` raised. A same-path retry then meets the existing file instead of returning the saved document. This is an ambiguous public outcome, especially when terminal index failure also disappears from background health. Return the durable document identity and its indexing status once source admission succeeds, or provide an idempotent retry contract. Test the API response against persisted state after inline parse/embedding failure; the batch tests currently use an `AsyncMock` document service (`server/tests/unit/api/test_source_batches.py:16-48`).

The document-index failure/health blind spot found in the parallel health scan is another general-ingestion intersection: a terminal indexing failure can leave retrieval without a document while the pending-index health signal clears. The health notebook owns its detailed evidence and remediation.

## Coverage assessment

- Focused unit suites for admission and scheduler pass **31 tests** (`uv run pytest -q tests/unit/core/ingestion/test_semantic_window_admission.py tests/unit/runtime/test_scheduler_contract.py`, 2026-10-08). They verify whole-exchange boundaries, failed/cancelled exclusion, policy capture, ordinary stage backoff, and local scheduler timeout reporting. They do **not** verify the two cross-layer defects above.
- The Postgres integration flow asserts durable window completion, Context revision, multi-session membership, and no graph extraction from an agent-derived block (`server/tests/integration/ingestion/test_project_semantic_postgres_flow.py:884-1002`). Another case verifies a `knowledge_committed` checkpoint survives resolver-publication failure and that recovery preserves source provenance (`server/tests/integration/ingestion/test_project_semantic_postgres_flow.py:1078-1255`). These are meaningful persisted-outcome checks, though the file substitutes a zero-Episode generator in every composed flow (`server/tests/integration/ingestion/test_project_semantic_postgres_flow.py:98-103,949,1168,1406,1541,1823`). Episode generation and storage have separate tests; the composed rich-Episode path remains unproved by this integration file.
- Selection/claim integration checks a participation toggle between proposal and claim and asserts no window is written (`server/tests/integration/ingestion/test_project_semantic_postgres_flow.py:647-706,710-879`). It does not cover failed/cancelled quiescence or the scheduler timeout. This review did not rerun Postgres tests; the prior review recorded local database setup timeouts in [handoff verification](intersection.md#verification).
- Filesystem tests check sequential create and replace behavior, and a document-service test checks cleanup after a single failed catalog insert (`server/tests/unit/core/knowledge/test_project_filesystem.py:32-49`; `server/tests/unit/core/knowledge/test_document_service.py:1127-1137`). They do not interleave two same-path uploads or assert catalog/file consistency after one insert loses.
- Document-index cancellation has a regression that requeues its durable claim (`server/tests/unit/core/knowledge/test_document_service.py:2390-2410`). Document-upload cancellation before a catalog row exists has no equivalent assertion; the source-batch cancellation test substitutes an `AsyncMock` service and checks only that the batch stops (`server/tests/unit/api/test_source_batches.py:52-58`).
- Local run of `test_project_filesystem.py`, `test_document_extraction_contract.py`, and `test_source_batches.py`: **40 passed, 3 failed**. The three failures were symlink-test setup on this Windows host (`os.symlink` raised `WinError 1314` before the filesystem methods were called). They are not evidence of a product failure; the passing parser and batch tests still use fake Docling/OCR or fake service calls for the boundaries above.

## Questions for follow-up

- Should timed-out semantic windows consume an automatic attempt even when the process is shutting down? A scheduler-imposed timeout should at least be distinguishable from an intentional shutdown cancellation.
- Should the frozen window also record model IDs used per stage, or is using the latest configured model on retry intended?
