# Artifact retention and cleanup

Working review, 2026-10-18. This traces artifact expiry, project file removal, and the document cleanup branches that intersect ingestion. The findings record the original defects; remediation status is below.

## Code path and rules

- Artifacts belong to an assistant message, session, project, and user. When a session is soft deleted, its original `deleted_at` remains fixed (`core/knowledge/db/writers/session_deletion_writer.py`). Artifact reads allow an open session or a deleted session less than 30 days old; every read uses owner/project scope (`common/artifact_retention.py`, `core/knowledge/db/readers/artifact_reader.py`).
- The application maintenance scheduler runs an artifact purge even with no project runtime loaded. Each sweep deletes at most 500 expired owned artifact rows in one PostgreSQL transaction, skips rows locked by another sweeper, and relies on FK cascade for revisions (`core/knowledge/jobs/application_maintenance_scheduler.py`, `core/knowledge/db/writers/artifact_retention_writer.py`). An unknown deletion time is not eligible. I found no confirmed defect in this narrow retention path.
- Hard project deletion commits database removal with a durable file-cleanup task, then removes the owned directory. Pending tasks retry at manager startup or on a repeated delete request (`core/project/project_manager.py:235-281,827-875`, `core/knowledge/db/writers/project_deletion_writer.py`). File removal avoids traversing symlinks and Windows reparse points (`core/knowledge/documents/filesystem.py:569-604`).
- Document admission writes local source bytes and a queued catalog row; reconciliation can later admit eligible local files as scan-managed documents (`core/knowledge/documents/service.py`). This makes failed file compensation an ingestion issue as well as a cleanup issue.

## Findings

1. **Project creation can leave an orphan source directory (active).** `create_project` writes `PROJECT.md` before its `try` around the database insert (`core/project/project_manager.py:321-357`). Cancellation during the worker or database transaction bypasses the `except Exception` cleanup; the worker may finish after cancellation. On an ordinary DB error, compensation deletes only `PROJECT.md`, leaving the new project directory. The current test asserts the file is absent, not that the whole directory is gone (`tests/unit/project/test_project_workspace_lifecycle.py:121-143`). Use a cancellation-safe owned operation and remove the newly created directory on failed creation, with cancellation and ordinary failure tests.
2. **Project deletion does not use the cross-process file lease (active when more than one server process accesses the library).** Document writes hold an OS mutation lease (`core/knowledge/documents/filesystem.py:113-169`, `service.py:192-221`). `ProjectManager.delete_project` checks only its own process's runtime lease map, then `remove_project_directory` deletes without acquiring the OS lease (`core/project/project_manager.py:845-875`, `core/knowledge/documents/filesystem.py:569-604`). Another process can still be editing that project's file and catalog. Serialize deletion against the same project mutation lease, and test two independent managers sharing a library.
3. **A failed project file cleanup is not retried during the same server run.** A failed removal returns `pending` and leaves the durable task. The manager scans tasks once at startup, and another DELETE can retry; the application maintenance loop runs artifact expiry and entity preflight, not pending project file cleanup (`core/project/project_manager.py:235-281`; `core/knowledge/jobs/application_maintenance_scheduler.py:94-109`). A transient startup failure can therefore leave project files until restart or manual retry. Add a bounded periodic retry, with a failed-once then successful cleanup test. This is a liveness gap in the current retry policy.
4. **Failed upload compensation can later turn a failed request into indexed content (active two-failure path).** When catalog admission fails, `_rollback_document_admission` attempts to delete source bytes, but logs and swallows local deletion failure (`core/knowledge/documents/service.py:1512-1546`). The orphan path can later be admitted by reconciliation as a scan-managed document (`service.py:375-448`). A caller has seen an upload error even though the source may later enter search. Cover catalog failure plus cleanup failure and the subsequent reconciliation. A durable orphan marker/cleanup or exclusion from reconciliation is needed until the failed admission settles.

## Existing known limit at this intersection

Full folder reconciliation reads and retains candidate bytes before the cumulative 500 MB preview limit (`core/knowledge/documents/service.py:243-336`). On a large tree, memory can exceed that budget. This was already recorded in [document service remediation](document-service-remediation.md#follow-up-branch-review-2026-10-17); this pass confirmed the code path but does not count it as a new finding. The fix needs bounded-memory admission with rules such as `.gitignore` still applied correctly.

## Coverage and verification

- Artifact retention has meaningful PostgreSQL contracts for owner and expiry boundaries, bounded batches, locked-row retry, cascade, and rollback (`tests/contract/storage/test_artifact_retention_contract.py`). I did not rerun PostgreSQL in this pass.
- Project deletion contracts assert durable cleanup-task state (`tests/contract/storage/test_project_deletion_writer_contract.py`); lifecycle tests cover restart/repeated-delete repair, not retry while a process stays up. Project creation's ordinary-failure test misses the directory and cancellation branches.
- Document service tests cover successful rollback after a catalog failure and periodic reconciliation. They do not cover the combined catalog-and-cleanup failure path. The large-tree memory case also lacks a bounded-memory assertion.
- The focused related unit suites passed **30 tests** on 2026-10-18. Passing these tests does not resolve the listed gaps; each missing branch needs an outcome assertion, not just a mocked call.

Suggested order: close the project creation cancellation gap; serialize deletion with edits; make pending cleanup retry while running; prevent failed upload leftovers from being indexed. Treat bounded-memory reconciliation as the existing separate document-service follow-up.

## Remediation and branch review (2026-10-18)

- Failed or cancelled project creation now settles its file/DB workers and removes the whole new project directory when the DB insert did not commit. Tests assert directory removal after an insert failure and cancellation during the file worker. If cancellation arrives after DB commit, the accepted project and its source remain together.
- Hard project deletion now holds the shared project file lease across DB deletion and directory cleanup. The filesystem removal path also takes that lease for direct callers; a two-instance filesystem test proves removal waits for an existing lease. Branch review found cancellation could release the lease while the removal thread was still running; cleanup now settles the worker first, with a cancellation test. Linked roots retain the guarded unlink path.
- Pending project file cleanup retries on each application maintenance interval, with errors isolated from artifact expiry and entity preflight. The retry test fails once and succeeds in the same process. The sweep visits all pending tasks so a permanently failing old task cannot starve later tasks; this is not a fixed-size batch.
- Failed upload admission now writes a durable hash marker outside the scanned project tree before publishing source bytes. If both catalog insertion and file compensation fail, reconciliation excludes those exact bytes after restart. Project deletion removes markers. Branch review found a second attempt at the same path could erase the first marker; marker creation now refuses replacement while source bytes remain. If the source has since been removed, the same file lease lets a new upload reclaim the marker. Tests cover both branches before reconciliation.
- Folder reconciliation now keeps paths and metadata, loading each file only while checking the scan rules and quota. A 24-file test asserts the admitted catalog rows and a bounded memory peak. This closes the previously recorded document-service memory issue, while preserving `.gitignore` processing.
- The affected unit suites passed **226 tests**; Ruff and `git diff --check` passed at that point. After starting the local PostgreSQL container, the broader affected storage run passed **60 tests**, including project deletion, conflict/advisory intersections, artifact retention, and document indexing. Full-book model indexing remains a separate Linux-machine check.
