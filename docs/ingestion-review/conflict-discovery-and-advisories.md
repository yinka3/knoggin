# Conflict discovery and relationship advisories

> Current verification (2026-10-19): see [verification status](verification-status.md) for the passing PostgreSQL runs, remaining coverage limits, and planned full Docling ingestion on Linux. Older database-unavailable statements below describe earlier runs.

Working review, 2026-10-18. This follows the current source and test assertions, including the handoff from Knowledge observations and entity merge. The findings record the original defects; remediation status is below.

## Code path and rules

- `ConflictDiscoveryJob` runs on the project scheduler's cadence when assisted mode has an LLM. It asks for possible ambiguity grounded in at least two listed observation IDs; it does not resolve truth or change the graph (`core/knowledge/jobs/conflict_discovery_job.py`, `common/schema/settings.py`).
- `ConflictDiscoveryReader` reads up to 128 active observations after a durable per-project cursor. `ConflictPacketBuilder` adds direct endpoint history, loads evidence provenance, then trims optional neighbors to the token ceiling. Only the accepted seed prefix advances the cursor (`core/knowledge/db/readers/conflict_discovery_reader.py`, `core/knowledge/conflict/conflict_discovery.py`).
- The model returns typed candidates. The job rejects IDs absent from the final packet. `ProjectMaintenanceService._persist_conflict_discovery` writes review groups and advances the cursor in one PostgreSQL transaction; notification follows commit (`core/project/maintenance_service.py:592`). These are sensible boundaries: the model suggests a review, and only cited stored observations can support it.
- `ConflictWriter` deduplicates by conflict kind and observation IDs, then compares evidence snapshot tokens. User resolution classifies the review; it does not rewrite evidence (`core/knowledge/db/writers/conflict_writer.py`, `core/knowledge/db/writers/maintenance_review_writer.py`).
- Relationship advisories group *unrecognized* labels by direction and endpoint types, requiring three eligible observations across at least two semantic windows and two endpoint pairs. Context-backed observations now qualify. An action records a proposal or decision but does not activate a domain relationship type (`core/knowledge/relationship_advisories.py`, `core/knowledge/db/writers/relationship_advisory_writer.py`).

## Findings

1. **A missing model field can silently consume conflict evidence (active path).** `LLMConflictDiscoveryResult.candidates` has `default_factory=list` (`conflicts.py:97`). A structured response missing `candidates` therefore becomes an empty list. The job treats it as a deliberate no-conflicts answer and commits cursor progress (`conflict_discovery_job.py:97-126`). The structured LLM adapter uses this model, so this is a real parser path. Require an explicit `candidates` field; keep `[]` valid, but let omission fail and retry without advancing the cursor. The existing empty-response unit test constructs `LLMConflictDiscoveryResult()` and therefore hides this distinction (`tests/unit/knowledge/test_conflict_discovery.py:460`).
2. **Entity merge leaves cited reviews current after relationship identity changes (active intersection).** Merge can rewrite endpoint IDs and `relationship_id`, or detach an observation after a self-loop or collision (`db/writers/global_entity_merge_writer.py:760-905`). It does not stale open reviews citing those observations. Other interpretation changes call `MaintenanceReviewWriter.mark_stale_for_observations` inside their transaction (`db/writers/relationship_interpretation_writer.py:219`). The evidence token omits endpoint and relationship identity (`db/readers/evidence_traversal_reader.py:74-91`, `evidence_service.py:286-296`), so normal freshness checks cannot notice this particular change. A conflict review may still describe the old entities. Test an open cited review through a normal merge and the collision/self-loop branches.
3. **Reinterpreted evidence cannot get a current conflict review through the usual paths (active intersection).** `ConflictWriter.record_detection` returns an existing review when its evidence `state_token` matches, without checking `status` (`db/writers/conflict_writer.py:99-104`). Relationship reinterpretation can stale a review while changing only `relationship_id`/`interpretation_source`, which the evidence token omits. Background discovery seeds only IDs greater than its cursor, so it does not revisit the changed observation (`db/readers/conflict_discovery_reader.py:50-80`). Even a later explicit detection with the same IDs and kind returns the stale review as resolved, without notifying anyone. A PostgreSQL regression should reclassify cited observations, rerun detection, and assert the returned status and notification policy. Preserve intentional dismissal deduplication for genuinely unchanged evidence.
4. **Provenance work can greatly exceed the model packet size (resource risk).** For each of up to 128 seeds, a new endpoint set can fetch up to 128 neighbors. `_render_complete_packet` loads and caches provenance for all optional rows *before* it trims them by token count (`conflict_discovery.py:77-128,164-196`). The run is indirectly bounded by seed and per-query limits, but may still fetch thousands of bundles to send a small final packet. Add a total neighbor/provenance work cap and a high-cardinality regression measuring loader calls.

## Dormant advisory path and latent defects

I found no production caller for `ProjectMaintenanceService.refresh_relationship_advisories` or `apply_relationship_advisory_action` in `server/src`. The only production observation insert found is `SemanticCommitWriter._write_relationships`, which adds a Context block link for each observation (`db/writers/semantic_commit_writer.py:1492-1541`). The advisory reader labels a linked observation `context`, while the builder requires independent occurrences (`db/readers/relationship_observation_reader.py:48-61`, `relationship_advisories.py:289-315`). Thus normal current ingestion cannot produce an advisory. The tests explicitly exercise independent rows built by fixtures (`tests/unit/knowledge/test_relationship_advisories.py:123-135`). This looks like a capability reserved for a future evidence source; it is not an active ingestion failure.

- **If independent observations become reachable, 129 IDs stop refresh.** The builder retains every ID in a pattern (`relationship_advisories.py:232-338`), while `refresh_relationship_advisories` passes the whole set to `EvidenceService`, which rejects more than 128 (`core/project/maintenance_service.py:299-328`, `core/knowledge/evidence_service.py:96-113`). One large pattern also prevents later patterns from refreshing. Bound or batch evidence, and test the 128/129 boundary before wiring this capability.
- **Advisory decisions and refresh are not atomic.** `RelationshipAdvisoryWriter` stales an old review, opens a successor, and may resolve it with separate transactions (`db/writers/relationship_advisory_writer.py:38-77,87-170`; `db/writers/maintenance_review_writer.py`). A failure can leave no open proposal or a pending review containing an accept/dismiss action. Use one transaction and a PostgreSQL failure injection test before exposing actions.

The apparent alternative issue of an unchanged refresh creating a second open review did **not** hold: `MaintenanceReviewWriter.open` uses a deterministic signature and reuses the existing review. Also, the missing `domain_status` SQL column is not by itself a misclassification: current recognized writes use `interpretation_source='domain'`, and the reader filters to `'observed'`.

Suggested order: protect the active conflict cursor; invalidate/recheck reviews on merge and reinterpretation; cap provenance work; decide whether advisories should be wired at all before repairing their latent paths.

## Remediation and branch review (2026-10-18)

- The model must now return `candidates` explicitly. An omitted field fails validation, leaving cursor progress uncommitted; an explicit empty list remains a valid no-conflict result.
- Entity merge now stales open reviews citing affected relationship observations in its merge transaction. Explicit re-detection can create a successor for a stale conflict even when its source-text evidence token is unchanged. PostgreSQL contracts now pass for merge invalidation and same-token re-detection.
- Packet building trims optional neighbors before provenance loading and caps total loaded provenance at 512 observations per run. The unit test measures loader calls on a high-cardinality neighborhood.
- Dormant advisories now cite at most 128 recent observations while keeping the full occurrence count. Refresh and action transitions use one database transaction and a per-pattern lock. A stale advisory refresh creates a new review even with the same evidence token; a changed domain version also supersedes the old open review. PostgreSQL rollback and successor contracts pass. The first successor contract run exposed a test fixture citing nonexistent observations; the fixture now inserts real rows, so its foreign keys and review evidence are checked.
- **Chosen policy:** scheduled conflict discovery scans new observation IDs after a monotone cursor. Staling an old review does not automatically send that old evidence to the model again. Explicit conflict detection can re-detect it. On 2026-10-18 the user chose to keep this explicit path instead of adding automatic model replay.
- Advisory refresh/action had no production caller at this point. The activation work below changes that status.
- After the fixture correction, the affected real PostgreSQL suites for conflicts, merge, advisory, project cleanup, artifact retention, and documents passed **60 tests** together on 2026-10-18.
- An adjacent PostgreSQL pass through conflict cursor reads, semantic commits, and Episode relationship enrichment passed **46 tests**, including the review-staleness handoff paths.

## Relationship advisory activation (2026-10-18)

- Context-backed observations now qualify for the evidence floor. The floor spans observations, distinct endpoint pairs, and distinct semantic windows; it does not claim the underlying source messages are fully independent. The old two-entity floor was automatically met by any one relationship, so a pair floor was added. Reviews remain suggestions and never add a `DomainConfig` relationship automatically.
- A project-owned job refreshes advisories on project startup, hourly thereafter, and when a semantic Knowledge commit wakes it. The hourly pass recovers from missed in-memory wake signals. The reader currently scans all active unrecognized observations and advisory review history for that project; this is a possible cost for large projects and should be measured before increasing the cadence.
- Advisory decisions have a dedicated public route, `POST /v1/projects/{project_id}/maintenance/relationship-advisories/{review_id}/decision`, with `accept`, `edit`, `dismiss`, `reopen`, and `suppress`. It checks the review's current evidence and domain version and rejects a superseded review ID. The generic maintenance decision route rejects advisory plans.
- The writer now refuses actions when no advisory review exists, so a direct internal call cannot create an evidence-free acceptance.
- A live PostgreSQL contract exposed an ambiguous-column error in the advisory reader's joined SQL. The selected columns and sort are now qualified. The same contract exercises Context-backed observation reading, scheduled refresh, review persistence and deduplication, decision transitions, and the fact that an accepted advisory leaves `DomainConfig` unchanged.
- The cited evidence is capped at 128 observations. The full occurrence count is stored in review state, so a count change outside the cited slice still supersedes an open proposal.
- Domain activation can recognize old observations without rewriting their `interpretation_source`. Refresh now checks each candidate against the current compiled domain, so it does not reopen an advisory for an already configured relationship with compatible endpoint types. The PostgreSQL contract covers that transition.
- Historical entity reclassification changes the endpoint types used in advisory pattern keys. It now stales open reviews citing observations whose endpoint type changed, in the same transaction as the classification update. A PostgreSQL contract covers this intersection.
- Verification: the focused advisory PostgreSQL contract passed 4 tests, including a failure injection proving type changes roll back when review invalidation fails. Focused advisory, factory, semantic, and API suites passed; generic maintenance and API port tests passed 45. Ruff and `git diff --check` passed on the touched files.
