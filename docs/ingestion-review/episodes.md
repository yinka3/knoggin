# Episode subsystem review

> Current verification (2026-10-19): see [verification status](verification-status.md) for the passing PostgreSQL runs, remaining coverage limits, and planned full Docling ingestion on Linux. Older database-unavailable statements below describe earlier runs.

Review started 2026-10-17. Source code and assertions are the authority; older README material may be stale. This pass covers Episode generation, policy, embedding, persistence, enrichment, retrieval, and the immediate semantic-window boundary. Project, session, and agent behavior is included only where it changes an Episode outcome. Findings below are review results, not fixes.

## Live path and system rules

1. A claimed semantic window owns frozen message membership and an Episode policy snapshot. The processor reloads those messages, skips generation for human edits or a disabled Episode policy, otherwise calls `EpisodeGenerator` (`core/ingestion/project_semantic_processor.py:411-453`; `core/knowledge/episodes/policy.py:23-113`).
2. The generator gives the hosted structured extraction model a readable catalog with window-local `message:N` handles. It permits zero to three proposals, resolves handles to actual messages, rejects overlap, enforces source-message/source-token/narrative limits, and embeds each resulting narrative with the local embedding service (`core/knowledge/episodes/build.py:41-135,162-212`; `core/knowledge/episodes/generator.py:91-144`; `common/schema/episode/generation.py:80-95`). The model chooses coherent topics; the server checks structural grounding and source IDs, not whether every narrative claim is true.
3. Episode IDs derive from the project and ordered source-message IDs. The embedding covers the maintained narrative, not raw evidence. The writer checks frozen membership and source sessions, then atomically inserts Episodes, their message links, and an `episode_result_recorded` checkpoint. A valid explicit empty result is a durable success (`core/knowledge/episodes/build.py:183-201`; `core/knowledge/episodes/embedding.py`; `core/knowledge/db/writers/episode_writer.py:52-162,391-422`).
4. Context may use the newly recorded Episodes as aids, but resolves their support back to frozen messages. Knowledge commits before Episode entity/relationship enrichment; finalization attaches graph links from active Context supports and completes the window (`core/knowledge/context/updater.py:174-184,223-235,296-302`; `core/ingestion/project_semantic_processor.py:503-547,732-793`; `core/knowledge/db/writers/episode_writer.py:164-313`).
5. Retrieval combines lexical and local-embedding ranks, with raw-message fallback when no Episode matches. A user edit regenerates its embedding before an atomic narrative/vector update, guarded by the prior `updated_at`; it marks the Episode `user_modified` (`core/knowledge/retrieval.py:194-307`; `core/knowledge/store.py:884-919`; `core/knowledge/db/writers/episode_writer.py:316-385`).

## Findings

1. **Narrative repair can silently change Episode evidence.** The repair prompt orders the model to preserve source references, but `EpisodeGenerator.generate_build()` only reapplies the repaired output after a character-limit error; it does not compare references or proposal count with the rejected draft (`core/knowledge/episodes/generator.py:122-135`; `common/templates/prompts/episode.md:55-69`). A scripted local repro changed an overlong proposal from `message:1` to `message:2`; the generator accepted and embedded an Episode sourced from the second message. This changes the source-derived ID and stored attachments, then can change what Context sees. The named repair test uses the same reference in both responses and asserts only prose and call count (`server/tests/unit/core/knowledge/episodes/test_episode_generator_contract.py:96-142`). Preserve each proposal's source-reference set and proposal count as a checked repair invariant.
2. **An omitted model result becomes a successful zero-Episode checkpoint.** `LLMEpisodeWindowDecision.proposals` has a default empty list (`common/schema/episode/generation.py:80-95`). Both `{}` and `{"proposals": []}` validate to the same result, though only the latter clearly requests omission. The writer then records the empty result as success (`core/knowledge/db/writers/episode_writer.py:52-65,147-162`). The existing decision test explicitly accepts an absent field (`server/tests/unit/core/knowledge/episodes/test_episode_decision_contract.py:96-97`). Require the `proposals` key while continuing to allow explicit `[]`.
3. **A scheduler timeout can charge an Episode that already committed.** `on_timeout()` compares window ID, stage, and attempt count, but not `episode_result_recorded` (`core/ingestion/project_semantic_processor.py:339-363`). The Episode writer commits that flag while leaving stage `claimed` and resetting attempt count to zero (`core/knowledge/db/writers/episode_writer.py:147-160`). If timeout cancellation arrives after the database commit on an initial attempt, the callback can record failure and backoff for the next Context stage. The durable failure writer checks only stage/count (`core/knowledge/db/writers/semantic_window_writer.py:256-287`). The timeout test blocks before Episode persistence, so this commit/cancel boundary is untested (`server/tests/unit/core/ingestion/test_semantic_window_admission.py:771-841`). This is a code-path race; a controlled commit/cancel regression is still needed.
4. **Window retry is broken in live PostgreSQL.** `retry_window()` uses `UPDATE ... AS window`, which PostgreSQL rejects at the alias (`core/knowledge/db/writers/semantic_window_writer.py:327-369`). In the live contract run, two retry tests failed with `SyntaxError: syntax error at or near "window"`: ordinary stage retry and legacy wrong-domain Context checkpoint repair (`server/tests/contract/storage/test_project_context_window_contract.py:864,1009`). This can keep a failed Episode window, and later stages, from explicit recovery. Use a legal alias and rerun both real database contracts.
5. **Episode relationship enrichment accepts part of a jointly sufficient support set.** The enrichment query joins an active relationship observation through any one observation block whose Context support message belongs to the Episode; it does not require all blocks in that observation's `support_key` set (`core/knowledge/db/writers/episode_writer.py:264-308`). Relationship observations are stored per independently sufficient block set (`core/knowledge/db/writers/semantic_commit_writer.py:1485-1539`). A live disposable-PostgreSQL probe created one observation requiring two blocks, each supported by a different message, and an Episode containing only the first message. Enrichment still inserted the relationship link with `source_message_count = 1`. That claims the complete relationship from incomplete Episode evidence. A regression should require at least one complete active observation support set within the Episode's messages before linking it.
6. **A valid character-bounded narrative can exceed the embedding model's token limit.** The default Episode cap is 4,000 narrative characters (`common/schema/settings.py:85-96`), while `EmbeddingService` rejects text beyond the loaded model's token limit rather than truncating it (`core/knowledge/services/embedding_service.py:493-521`). A locally accepted 3,299-character Episode summary produced 1,803 tokens with the cached Stella tokenizer; its configured limit is 512. The embedding input guard raised `ValueError` before encoding, so this Episode would consume stage retries and hold later stages. This probe used the actual cached tokenizer and limit config, but did not load the large Stella model or complete an ingestion. Align generation and embedding limits without silently dropping content.

## Remediation follow-up (2026-10-17)

All six findings above have code fixes and behavioral regressions:

1. Narrative repair now rejects a changed proposal count or source-reference set before embedding. Explicit `{"proposals": []}` still records a valid empty result; an omitted `proposals` key now fails validation.
2. The scheduler timeout callback compares `episode_result_recorded`, and the failure SQL checks that same checkpoint atomically with the stage and attempt count. A controlled scheduler test pauses after Episode commit; a PostgreSQL contract checks the read-then-commit race. Neither charges the next Context stage.
3. Explicit retry uses the legal `semantic_window` SQL alias. Both previously failing PostgreSQL retry contracts pass.
4. Episode enrichment requires every block of at least one active relationship observation to have support in the Episode. It rebuilds the window's links, so a retry also removes stale partial or retired links. Relationship reinterpretation uses the same complete-support rule and no longer recreates partial links. Its previously untested SQL insert also needed `"symmetric"` quoted.
5. A later Knowledge commit now reconciles earlier Episodes when it retires observations. A PostgreSQL regression keeps a relationship active through one block while retiring another; the older Episode loses its unsupported link. Unused Episode writer helpers that implemented the former per-message linking approach were removed.
6. Episode generation, user edits, and embedding rebuild now split a long narrative with the loaded tokenizer at the model's real limit. They encode every chunk and pool the vectors into one normalized Episode vector. Short narratives retain their previous vector. A test with the cached Stella tokenizer confirms that a policy-valid narrative over 512 tokens is split without losing characters. Pooling is a retrieval heuristic; its ranking quality still needs real-world evaluation.

Verification after the fixes: **70 Episode, embedding, and semantic-window unit tests passed**; **19 Episode storage contracts passed**; **3 focused PostgreSQL ingestion/retry contracts passed**. The full Knowledge commit and Episode enrichment contract run had **39 passed, 1 failed**: the new retired-ID variable was unset when a window reused a published Context revision. After initializing that branch, both the reused-Context case and the retirement case passed on rerun. The non-empty composed ingestion test uses real PostgreSQL through Episode, Context, Knowledge, and finalization, with scripted generation and a synthetic vector. The relationship regression uses real PostgreSQL and complete/partial support sets. A full Stella-weight encode and retrieval-quality run were not performed on this Windows machine.

## New intersection finding to follow up

`GlobalEntityMergeWriter` copied Episode relationship links when two entity IDs merged. If the old and surviving relationship IDs both occurred in the same Episode, its `ON CONFLICT` branch **added** their `source_message_count` values. The same message can support both observations, so that sum could overcount. A live PostgreSQL regression also showed that the merge's unchanged-survivor relationship branch deleted its own Episode links. Self-loop collapse discarded links without journaling them, and rollback deleted newly created relationship rows before moving their observations back.

## Entity merge intersection remediation (2026-10-17)

- Changed relationships now recompute Episode link counts from distinct messages supporting complete, active observations in the Episode's Context revision. An unchanged relationship keeps its existing link. Entity link counts use the same revision boundary and distinct-message rule, avoiding overlap and support from old blocks. The merge journal stores the exact original Episode rows for rollback.
- Rollback restores old relationship rows first, moves their observations and Episode links, then removes any merge-created target row. Relationship and dependent evidence roll back as a group. If someone changes a link or adds evidence after the merge, the plan flags the group and a partial rollback leaves that evidence in place.
- `test_global_entity_merge_episode_contract.py` exercises overlapping and distinct support, an old Context block, self-loop collapse, a newly created target relationship, exact Episode entity/link restoration, and partial rollback with changed and newly added evidence. All five live PostgreSQL cases pass. The adjacent maintenance candidate test had a fixture that violated project visibility rules before reaching its assertion; its seed was repaired and the test passes. The first broader run had **21 passed, 1 failed** from that fixture; the failed test passed on rerun. Ruff passes on the changed writer and contract.
