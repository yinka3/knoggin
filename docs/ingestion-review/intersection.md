# Extraction and Knowledge handoff

Working notes based on source and tests (2026-10-08). The root README is treated as background; paths below are the source of truth for this review.

## Pipeline map

1. `SemanticWindowAdmission` selects whole, sealed exchanges in per-session order, closes at the configured token target or after an idle/explicit flush, and stores membership plus policy snapshots (`server/src/core/ingestion/semantic_window_admission.py:101-199`, `:230-323`).
2. `ProjectSemanticProcessor` drains a durable window through Episode, Context, Knowledge, and finalization checkpoints, reloading state after each stage (`server/src/core/ingestion/project_semantic_processor.py:268-346`). A human edit creates its own Context-committed window and skips the Episode/Context LLM stages (`server/src/core/knowledge/context/projection.py:354-385`).
3. Knowledge reloads the committed Context revision, its persisted impact closure, block supports, and frozen window messages. Entity resolution runs before relationship extraction; one targeted entity recovery pass can follow an unknown relationship endpoint (`server/src/core/ingestion/project_semantic_processor.py:597-659`).
4. `SemanticWindowBuild` allows extraction only from impacted, current `user_asserted`, `source_grounded`, or `human_asserted` blocks. It checks that mentions, entity associations, and relationship endpoints cite eligible blocks and resolved entities (`server/src/core/ingestion/batch.py:147-232`).
5. `SemanticCommitWriter` rechecks the Context revision and impact closure against SQL, writes entities/relationships, retires stale observations, rebuilds the graph projection, and advances to `knowledge_committed` in one transaction (`server/src/core/knowledge/db/writers/semantic_commit_writer.py:74-225`, `:235-340`). Finalization then publishes resolver IDs and enriches Episodes (`server/src/core/ingestion/project_semantic_processor.py:679-742`).

## Rules visible in code

- Context is the canonical semantic input; the editable `CONTEXT.md` is a guarded projection (`server/src/core/knowledge/context/projection.py:110-168`, `:170-246`).
- A window freezes domain and ingestion policy so retries use the admitted rules (`server/src/core/ingestion/semantic_window_admission.py:168-198`, `server/src/core/ingestion/policy.py:63-136`).
- The graph favors provenance and abstention: relationship output needs typed local entity handles and cited Context blocks, and unknown endpoints are diagnostics rather than invented entities (`server/src/common/templates/prompts/extraction.md:92-127`, `server/src/core/ingestion/relationship_extractor.py:192-240`).
- General document ingestion extracts and indexes searchable chunks separately (`server/src/core/knowledge/documents/indexer.py:103-173`). `CONTEXT.md` is excluded from that generic file path (`server/src/core/knowledge/documents/service.py:1136-1142`). Retrieved material reaches this semantic path through saved assistant source references, which the Context updater receives with the frozen window messages (`server/src/core/knowledge/store.py:212-249`, `server/src/core/ingestion/project_semantic_processor.py:498-513`).

## Findings and validation gaps

- **Fixed in the current worktree: a domain-version change could strand the next no-op semantic window.** The Context stage now creates a zero-impact revision at the window's frozen domain version when there are no Context edits. The writer's equal-hash shortcut now checks the domain version too, so it cannot discard that bridge. The focused Context/Knowledge/build-validation suite passes **51 tests** and Ruff passes. A Postgres writer contract test was added and collected, but not run because local Postgres is unavailable. The downstream failure chain remains documented above as the reason for the fix; integration coverage for following-window admission is still open.
- **Fixed: section removal and title/order changes during domain activation.** Activation locks the project row and then the Context root, matching project deletion and Context revision commits. It rejects removal when current blocks use that section and waits for active windows to finish, so a retry cannot reopen Context under old frozen rules (`server/src/core/project/domain_config_store.py`, `server/src/core/knowledge/db/writers/project_context_writer.py`). Explicit retry reopens a legacy checkpoint when its Context revision has the wrong domain version (`server/src/core/knowledge/db/writers/semantic_window_writer.py`). A clean generated projection now repairs after a title change before or after the zero-impact bridge; a file with user edits still conflicts. Focused tests pass, but the Postgres contracts remain unrun locally.
- **Implemented in the current worktree: preserve each relationship support and label.** The extractor deduplicates only exact combinations of endpoints, normalized relationship, observed label, and support block set. The SQL key now includes a stable support-set hash; each independent set or observed label has its own observation row. Retirement therefore removes only the affected evidence row, and the graph aggregate remains while another row is active. Global merge collision matching now keeps different support keys distinct. Two adjacent stale-evidence paths were also fixed: reclassification scans active observations only and its writer treats retired rows as conflicts; a semantic commit marks open reviews citing retired observations stale in the same transaction. A storage contract checks persistence, replay, retirement, review staleness, and stale-plan rejection. It collects, but the real Postgres test did not complete setup locally, so durable behavior remains unverified.

- **Fixed in the current worktree: merge shortlist ranking applied too late.** The SQL previously limited pairs ordered by entity IDs; the tool sorted that partial set by message evidence only afterward. A strong pair could be omitted before the tool saw it. The query now orders by distinct supporting-message count and stable IDs before `LIMIT`. A Postgres contract seeds a lower-ID weak pair and a later strong pair, then asks for one result. The contract collects; Postgres is still needed to verify the actual query result.
- **Fixed in the current worktree: merge review inputs were not fully validated.** Unsupported evidence kinds could skip candidate-membership validation. `propose()` now allows only message and episode references that belong to one of the two candidates, rejects previews with unresolved project Context conflicts, and can reject a stale expected state hash before opening review. Unit tests cover the invalid evidence path and query ordering. The existing state-checked review/merge path is unchanged.
- **Source-only entity names now stay unresolved.** The structured fallback checks the local message reference and exact quote, then records the proposal in a transient issue without adding a Context entity association. JEV does not send source-only candidates to its provider. The NLI loader, model configuration, and CI artifact were removed. The quote is not durable as a review item; retaining proposals across windows would need a separate storage path.
- **Merge model advisor now has an explicit tool.** After the user approved sending bounded stored evidence to the configured model, `advise_entity_merge` selects `merge_model`, supplies scoped excerpts, and validates cited IDs. Its recommendation does not open or apply a review. `propose_entity_merge` can use the returned state hash and evidence IDs, while the existing review and confirmed-merge checks remain in control (`server/src/core/knowledge/entity/merge_advisor.py`; `server/src/core/agent/tools/maintenance.py`).
