# Document service review

First-pass review, 2026-10-12. Source code is the authority; older README material may be stale. This review covers the document service and its associated structures, including branches already visited during the general ingestion and common-layer reviews. Findings are review results, not fixes.

Implementation and verification are tracked in [document-service-remediation.md](document-service-remediation.md).

## Review method

1. Map entry points, owned data, background work, readers, and cleanup paths.
2. Trace each branch into its callers and downstream storage, retrieval, agent, source-reference, and health effects.
3. Write down rules implied by validation and code, including deliberate limits and tradeoffs.
4. Check tests for meaningful assertions at boundaries and for realistic failure paths.
5. Record defects with a concrete path and cascade; distinguish confirmed defects from hypotheses. Plan fixes after the scan.

## Code map

- `core/knowledge/documents/service.py`: project-scoped facade for local project files, catalog admission, reads, search, saved links, user attachments, and reconciliation. File/catalog mutations use a project mutation lease; cancellation is shielded until owned work settles.
- `core/knowledge/documents/indexer.py`: claimed durable indexing work, extraction, embedding, publication, retries, startup recovery, reconciliation wakeups, and health counters. `DocumentIndexPolicy` snapshots admission limits.
- `core/knowledge/documents/extraction.py`: format-specific parsing, Docling/native PDF layout, chunking, and parse snapshots.
- `core/knowledge/documents/filesystem.py` and `scanning.py`: canonical project tree, safe mutation and path handling, folder admission policy.
- `core/knowledge/db/readers/document_reader.py` and `writers/document_writer.py`: project-scoped catalog, chunk, parse-snapshot, and search persistence.
- `core/knowledge/documents/read_service.py`: narrow read-only adapter used by community runtime; it delegates to `DocumentService`.
- `common/schema/document.py` and `common/schema/source/*`: attachment/folder/focus/link contracts and source locations.
- `runtime/project_factory.py`, `runtime/api_port.py`, `core/agent/tools/search.py`, and `core/agent/tools/workspace.py`: runtime ownership, public admission, agent reads/search, focus constraints, and source-reference creation.

## Live contract and system opinions

- A project has one local source tree and one project-scoped document catalog. Upload admission writes source bytes and a queued row first; parsing, chunks, and embeddings are derived work. A project mutation lease orders Knoggin-owned file and catalog changes (`service.py:192-220,1161-1292`; `filesystem.py:85-188`).
- Document parsing and retrieval models run locally: PDF/DOCX use a serialized CPU Docling converter with OCR and table structure, images use Tesseract, and indexing/query use the shared embedding model (default Stella); optional search reranking uses the shared cross-encoder (default BGE). The default embedding backend is ONNX, with Torch configurable. The document path does not invoke the hosted extraction LLM (`extraction.py:195-216,344-440`; `services/embedding_service.py:108-170,254-378,392-510`; `runtime/resources.py:281-285`).
- Indexing claims a queued row, reads and hashes the current source, creates an immutable parse snapshot and chunks, then publishes the current snapshot and chunks in one writer operation. A stale source/catalog hash sends the claim through reconciliation rather than publishing stale evidence (`indexer.py:104-181`; `writers/document_writer.py`).
- Ordinary source files and user uploads are separate admission routes. Reconciliation is meant to apply folder filters, `.gitignore`, file limits, and a 10,000-file safety bound to local files. Scan settings changes clear the fingerprint cache (`service.py:222-387,736-792`; `scanning.py`).
- Read and search favor visible, non-deleted current documents. The service limits passages, search results, candidate sets, and rerank work. PDF reads use page locators; text/code/CSV use line or row locators. Exact client selections require the same content hash and snapshot ID (`service.py:824-1125,1633-1769`; `readers/document_reader.py`).
- Transient user sources can stay run-local; saved web links store a URL bookmark without indexing web content. Assistant-observed web sources require an explicit promotion call (`service.py:1392-1629`).
- Delete removes current chunks and tombstones the catalog row but intentionally retains immutable parse snapshots and previously saved source excerpts for historical provenance (`db/writers/document_writer.py:266-318`; `db/readers/document_reader.py:226-258`; `db/readers/source_reference_reader.py:278-306`). The `delete_document` docstring's word "Purge" is therefore ambiguous if a caller expects full erasure; tests assert retained historical content (`test_document_reader_scope_contract.py:132-158`; `test_source_reference_storage_contract.py:826-855`).

## Confirmed defects and cascades

1. **Mixed native/OCR PDF index pages can lose OCR text.** If Docling labels any table on a page `document_index` and `_native_pdf_cells` returns at least one cell, `_extract_docling_snapshot` replaces the *whole page* markdown with native text (`extraction.py:645-703`). On a mixed page, OCR-only text outside those native cells disappears from the canonical snapshot, chunks, indexed search, page reads, and client selections (`extraction.py:735-759`; `indexer.py:135-165`; `service.py:856-1125`). A fake mixed-page Docling/native-cell reproduction showed an OCR-only appendix line missing. The existing index-page test exercises native-only text; storage and public-runtime format tests monkeypatch `_extract_docling_snapshot`, so they do not prove this handoff. Repair needs region-level preservation or a conservative no-loss fallback and a mixed native/OCR test that checks both snapshot and chunks.
2. **Incremental reconciliation can apply folder rules to the wrong set.** It skips unchanged files by size/mtime fingerprint, then calls `preview_folder` with only changed files (`service.py:274-301`). The preview builds `.gitignore` rules from the entries it receives and enforces file count/total byte limits within that same batch (`scanning.py:182-197,487-515`). Thus a new file ignored by an unchanged `.gitignore` can be cataloged and indexed. A new ignore rule can leave existing content indexed. A project already at the scan count/size limit can admit more files across passes. `_reconcile_owned_file_changes` also previews only upserts, so owned edits miss surrounding `.gitignore` context (`service.py:389-458`). The periodic full-hash pass occurs every tenth reconciliation; a runtime restart or settings change may force an earlier full pass. Test complete and incremental manifests together, including ignored file creation, rule edits, and cumulative limits.
3. **Restrictive subtree focus is bypassed by agent search with `document_name`.** `search_project_documents` passes neither an ID nor path to `_require_focus_document` for a name selector, skips the focus subtree default, resolves that name from all visible documents, and searches its ID (`core/agent/tools/search.py:886-975`). Direct ID read/info routes do check subtree containment (`search.py:468-473,753-754,792-793`). A named document elsewhere in a readable project is therefore reachable outside the required subtree. Existing tests cover restrictive exact-document focus and preferred subtree focus, not this combination. Constrain name lookup and resulting search to the required subtree and test an outside name.
4. **Agent document-name lookup sees only the newest 1,000 rows.** The tool lists `limit=1000` and resolves names in that result (`core/agent/tools/search.py:919-967`; `service.py:1633-1651`). Older indexed documents can be reported missing; duplicate names outside the window can be missed. General SQL search itself is not capped to 1,000 documents, but the tool returns `[]` early if those 1,000 contain no indexed row, even when older indexed documents exist. The fake service in agent tests ignores `limit`, so it cannot catch this. Resolve names in a bounded SQL query over the full visible set and test >1,000 rows and name collisions.
5. **Mixed/unknown PDF page reads lose agent source context.** The page read can produce a `layout_region` locator with `extraction_method=mixed` or `unknown` (`service.py:880-904`), and the source schema accepts both (`common/schema/source/locators.py`). The agent source normalizer omits those methods (`core/agent/tools/search.py:74-85`), so a readable page may have no `source_context` for durable provenance. Align the normalizer with the schema and test read-to-reference behavior for mixed and unknown pages.
6. **One long code line or CSV row escapes the chunk target.** Code and CSV splitting only cut between lines/rows (`extraction.py:903-941,1167-1219`). An accepted source can therefore yield a very large chunk; the local ONNX embedding tokenizer truncates its input (`services/embedding_service.py:72-77`), leaving later text with no vector representation. Retrieval and rerank also handle an oversized chunk. Decide between safe sub-line/sub-row locators and a clear admission error, then test a large single line/row and whether late text is retrievable.
7. **A stale restricted request focus can silently become an unrestricted run.** API admission resolves the requested target (`runtime/api_port.py:829-872`), but the orchestrator resolves it again before building tools (`core/agent/orchestrator.py:113-126,315-350`). A missing/inaccessible target at that later point is caught and turned into `None` for request and pinned focus alike. The tools are then bootstrapped without a restriction. Deleting or renaming the target between admission and execution can broaden a run whose request specified `behavior=restrict`. The stale-focus test covers a pinned subtree preference, not a restricted request (`test_orchestrator.py:533`). Reject stale restricted request focus at execution; test that it produces an error before unrestricted tools run.
8. **A selected document passage fails before agent execution.** `DocumentService.resolve_document_selection` returns a `parse_snapshot_id`, but `AgentOrchestrator._resolve_document_selection_context` drops it (`service.py:906-1125`; `core/agent/orchestrator.py:352-386`). The initial source builder requires that ID and raises `ValueError` (`orchestrator.py:150-159,283-313`; `core/agent/sources/document_selection.py:24-45`). The orchestrator catches it as a generic run error before the executor starts. The selection unit test asserts the incomplete dict in isolation and the builder unit test supplies a complete dict; no test joins them (`test_orchestrator.py:556-630`). Preserve the ID through selection context and test an actual selected-passage run through candidate creation.
9. **File mutations can report failure after changing the source, leaving old catalog/search state.** Native create/update/append/move/delete modify the file before `_reconcile_owned_file_changes` updates the catalog (`service.py:577-703,389-458`). Ordinary preview/DB failures have no file compensation. `delete_document` similarly removes the source before tombstoning its row (`service.py:1127-1159`). A failed call can leave an old live row and chunks searchable until periodic/startup repair; a retry can then find the source missing or path already occupied. Cancellation is settled, but that does not handle ordinary failures. Existing periodic reconciliation rollback tests do not exercise this mutation boundary (`test_document_service.py:1396`). Define an error/repair contract and test writer failure after each kind of file mutation, especially delete.
10. **Reindexing a linked readable document can falsely report success.** The indexer fetches the ID with a reader that includes linked readable projects, but the writer can transition only the active project's rows (`indexer.py:115-139`; `db/writers/document_writer.py:319-382`). For a foreign document, the transition returns `None`; the indexer rereads and returns the unchanged row, and the public reindex endpoint returns it as success (`runtime/api_port.py:650-652`). Delete explicitly checks ownership; reindex does not (`service.py:1136-1141`). Reject reindex of a non-owned document and test a linked readable project.
11. **Concurrent partial bookmark updates can erase each other.** `update_saved_web_link` reads the row, merges an omitted field in Python, then the writer updates both title and summary (`service.py:1579-1613`; `db/writers/document_writer.py:751-788`). Two requests changing different fields can both read the old row and the last writer can restore the other's old value. The current partial-update test is sequential (`test_saved_web_links.py:184-210`). Update only supplied fields atomically, or lock the row through the read/merge/write transaction; test interleaved requests.
12. **Windows junctions can escape the project filesystem boundary.** The normal root and read/write/path-walk checks test `is_symlink()` but not `is_junction()` or the Windows reparse-point flag (`filesystem.py:59-78,394-450,459-470`). On this Python 3.12 Windows host, a temporary NTFS junction reported `is_junction=True`, `is_symlink=False`, and `DirEntry.is_dir(follow_symlinks=False)=True`. `iter_paths` therefore descends into an external directory; read and write/delete path checks can also traverse it. A project root or library root that is a junction can redirect the whole tree. This can catalog outside files and operate on them through a project-relative name. A junction cycle can make the scan recurse repeatedly without cycle detection. The project-deletion walker already treats reparse points as boundaries (`filesystem.py:485-534`), but normal access does not. Add Windows junction regressions for roots, scan, read, write, and delete; reject reparse points consistently. Existing tests check symlinks for ordinary access and junctions only for project removal (`test_project_filesystem.py:199-220,262-293`).
13. **The 10,000-file reconciliation cap does not bound the filesystem walk.** `ProjectFilesystem.iter_paths(limit=...)` collects every file under the tree, then sorts and slices its result (`filesystem.py:389-416`). Reconciliation requests 10,001 paths to detect an oversized tree, but discovery can already traverse and retain an arbitrarily large tree before that guard executes (`service.py:235-241`). `list_project_files` similarly walks the full tree before returning at most 100 (`service.py:464-503`). Stop traversal at a safe bound, or use a bounded order-aware listing strategy; add a test that proves enumeration itself stops when the cap is crossed.

## Likely defect requiring failure-path reproduction

- **A transient database error may strand pending index work.** `_drain_durable_work` logs an unexpected error and exits (`indexer.py:443-471`). It restarts on an explicit `_request_drain`, but an unchanged periodic reconciliation does not request one (`indexer.py:522-539`). If the read of due/pending work fails once and no new document or catalog change occurs after recovery, queued work appears to wait indefinitely in that loaded runtime. Health can report pending work with no active indexing loop but does not restart it (`core/health/service.py:599-605`). Reproduce a one-time reader failure followed by recovery, and assert the durable row eventually indexes without a fresh upload.

## Coverage notes

- Passing tests do not certify a composed path if they substitute the parser, service, or limit handling. The parser's native-only index test and the storage/runtime tests using a mocked Docling snapshot leave mixed-page loss untested (`test_document_extraction_contract.py:398`; `test_document_format_indexing.py:213`; `test_document_format_runtime.py:258`).
- Folder-preview tests verify `.gitignore` against a complete manifest; service tests verify incremental fingerprint skipping. Neither tests their interaction (`test_folder_preview.py:241`; `test_document_service.py:1461`).
- Agent focus and name tests do not exercise restrictive subtree plus `document_name` or enforce the service's 1,000-row cap (`test_document_search_contract.py:25,518-580,894-913`).
- Selected-passage orchestration tests stop before initial source-candidate construction, while builder tests provide the field dropped by the orchestrator (`test_orchestrator.py:556-630`; `core/agent/sources/document_selection.py:24-45`).
- The real Postgres scope/provenance tests do cover readable-project snapshot access, current-pointer changes, tombstones, and retained historical source references (`test_document_reader_scope_contract.py:86-158`; `test_source_reference_storage_contract.py:806-1035`). They do not prove the linked-project reindex ownership boundary.
- Batch admission tests cover size limits, ordered per-item failures, safe public errors, and cancellation, but use a fake document service for the storage step (`test_source_batches.py:32-112`). Document service tests do exercise owned file/catalog ordering and cancellation; they do not inject a writer failure *after* a native file mutation (`test_document_service.py:1196-1339,1490-1668`).
- Filesystem tests prove symlink exclusion and junction-safe project removal, but not regular document access through a junction (`test_project_filesystem.py:199-220,262-293`).
- This review has traced code and test assertions. It has not run the full test suite or a real Docling/Postgres integration in this pass.

## Remediation order for discussion

1. Close confinement/focus failures: junction traversal, stale restricted focus, and subtree name search.
2. Restore evidence correctness: selected-passage candidate, mixed PDF page text, incremental scan policy, and mixed/unknown PDF source context.
3. Repair mutation and background work failure paths: file/catalog compensation and durable-drain recovery; reproduce the latter first.
4. Address scale and remaining contracts: full-tree walk, 1,000-row name lookup, oversized chunks, linked-project reindex result, and bookmark update race.

The review also leaves two behavior questions: should changing scan settings immediately remove now-excluded indexed content (the current code waits for periodic reconciliation), and should document deletion mean full erasure or historical provenance retention? The code currently implements delayed application and provenance retention; these are not counted as defects without the product contract.
