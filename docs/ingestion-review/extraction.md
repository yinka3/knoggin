## Path through the system

1. The semantic processor reopens a committed Context revision and its durable impact closure, builds entities, runs relationship extraction, optionally rebuilds entities and relationships once for unknown endpoints, then commits Knowledge (`server/src/core/ingestion/project_semantic_processor.py:597-659`). Only current user asserted, source grounded, and human asserted Context blocks are extraction inputs (`server/src/core/ingestion/batch.py:147-163`).
2. Entity extraction concatenates eligible blocks with offset tracking, matches known aliases, and runs local VP-01 GLiNER2.5 (`server/src/core/ingestion/text_processor.py:38-67,208-355`). English and multilingual checkpoints are selected by the frozen domain language (`server/src/core/ingestion/vp01.py:10-12,49-56`); GLiNER labels/descriptions come from that domain (`vp01.py:59-75`). The model runs through `ModelWorkCoordinator` as background work (`text_processor.py:125-153,302-314`).
3. Meaningful blocks without candidates, known alias gaps, and unknown relationship endpoints can trigger entity fallback (`text_processor.py:579-643`). Optional JEV first judges literal candidates from endpoint diagnostics or known aliases (`text_processor.py:645-739`); in active mode positive judgments add mentions before the fallback LLM (`text_processor.py:387-458`). JEV is disabled by default, has observe and active modes, and pins `jev-1.13.0` in policy (`server/src/common/schema/jev.py:25-34`). Its work is bounded by calls, observations, time, request size, and spending admission (`server/src/infrastructure/jev_client.py:43-83,109-175,262-279`). A JEV provider error degrades to the normal fallback path (`text_processor.py:798-807`).
4. The larger extraction LLM handles remaining entity gaps and all VP-02 relationship extraction (`text_processor.py:527-534`; `server/src/core/ingestion/relationship_extractor.py:159-190`). It uses the configured `extraction_model`; runtime settings default to `google/gemini-2.5-flash-preview` (`server/src/common/schema/settings.py:169-175`; `server/src/runtime/resources.py:261-270`). `generate_structured` uses Instructor/Pydantic, with three validation retries and separate provider usage accounting (`server/src/infrastructure/llm_client.py:43-44,519-604`). Entity and relationship schemas require local `bN` block and `eN` entity handles rather than durable IDs (`server/src/common/schema/ingestion/extraction.py:36-54,108-151`).
5. Resolved entities are assembled into pending writes; canonical message references are only attached after a literal match in the frozen supporting message (`server/src/core/ingestion/context_entity_build.py:61-104`). VP-02 receives the resolved entity candidates plus current Context blocks and stores typed relationship writes after handle, block, self edge, and domain normalization checks (`server/src/core/ingestion/relationship_extractor.py:64-135,241-328`). The Knowledge writer checks eligible blocks and endpoint classifications again before committing (`server/src/core/knowledge/db/writers/semantic_commit_writer.py:1408-1517,1557-1575`).

## Rules and opinions visible in code

- Context is the authoritative extraction surface, with the impact closure controlling what gets reconsidered. Agent derived blocks are excluded (`batch.py:147-163`). Cross block entity spans are allowed and deliberately tested (`server/tests/unit/core/ingestion/test_context_entity_build.py:431-459`).
- Known aliases and local GLiNER go first. The LLM is a targeted fallback for entity gaps, but VP-02 relationships always use the extraction LLM (`text_processor.py:208-355,358-376`; `relationship_extractor.py:159-190`).
- **Current source-only rule:** if a name is absent from a Context block, structured fallback must return a local message reference and an exact quote containing the name. A valid proposal becomes an unresolved issue for the current build; it does not create an entity association. JEV evaluates block-literal candidates only. The local NLI model, loader, and runtime configuration were removed (`text_processor.py`; `server/src/common/templates/prompts/extraction.md`; `server/src/core/knowledge/services/embedding_service.py`).
- **Review gap:** `SemanticWindowBuild.issues` is transient. The supporting message remains stored, but the proposed name and quote are not durable review items. A later review feature would need its own typed storage path.
- Relationship extraction is conservative in its prompt: explicit or physically implied relation, no co mention edge, smallest sufficient block set (`extraction.md:92-128`). The program validates citation membership and endpoint handles, but does not independently check that the cited prose entails the edge (`relationship_extractor.py:241-299`). This puts the semantic grounding decision on VP-02; a valid but invented edge can reach persistence.
- Unknown endpoint diagnostics trigger one bounded second entity/relationship pass before commit (`project_semantic_processor.py:651-659`). The JEV budget is shared across both passes (`context_entity_build.py:127-148`), and previous accepted extraction decisions are reused only for an unchanged fingerprint (`text_processor.py:759-795`).

## Findings with downstream effects

### 1. Independent relationship evidence can be lost (high confidence)

VP-02 can return the same edge with separate sufficient supports, such as `[b1]` and `[b2]`. The extractor groups writes by `(entity_a_id, entity_b_id, relationship_type)` and keeps only the shortest support tuple (`server/src/core/ingestion/relationship_extractor.py:309-320`). The writer records only that tuple (`server/src/core/knowledge/db/writers/semantic_commit_writer.py:1508-1517`). If its selected block is replaced, the observation retires when **any** stored support is no longer current (`semantic_commit_writer.py:1352-1373`). The other independently sufficient block may still exist but its evidence was never saved; if it falls outside the next impact closure, no new observation repairs the edge. With no active observation, the graph aggregate is deleted (`semantic_commit_writer.py:1577-1609`). This affects graph answers and evidence history, not just trace counts. Simply unioning the two support sets would still fail because retirement treats stored blocks as jointly required. The persistence identity needs to preserve separate sufficient evidence groups.

Current status: implemented in the worktree. The extractor now deduplicates only exact combinations of endpoint, normalized relationship, observed label, and support set. Each distinct sufficient set has its own observation row and stable support key; the one-time schema upgrade preserves each old row's block set. Context retirement removes only rows whose required blocks are no longer current. The global entity merge writer includes the support key when detecting collisions. A new contract checks persisted groups, single-support retirement, stale reviews, and stale-plan rejection, but local Postgres setup did not complete.

Coverage: a new extractor unit test uses the same edge and label with `[b1]` and `[b2]`, a second observed label, and an exact duplicate. The storage regression checks that removing `b1` retires only its groups while `[b2]` keeps the graph edge. It also checks that cited reviews become stale and stale plans conflict.

### 2. Distinct observed relationship labels can be discarded (high confidence)

The domain may map several labels to one canonical relationship (`server/src/common/conf/domain_config.py:339-369,839-859`; `server/src/common/conf/relationship_config.py:82-115`). The old extractor dedup key omitted `observed_label` (`relationship_extractor.py:279-320`), so distinct labels for one pair could collapse before commit. The writer's observation key includes `observed_relationship_label` (`semantic_commit_writer.py:1469-1499`), so storage was already shaped to retain that distinction. The extractor now includes the normalized observed label and support set in its dedup identity. Unit and Postgres contract regressions cover two labels mapped to one canonical type; the storage test awaits a working database.

### 3. JEV candidate enumeration before its call budget (fixed work bound)

Candidate preparation used to fetch a profile for every alias and scan every gap before `JevWorkBudget` applied. It now stops after 512 literal checks, respects the shared remaining observation count, and fetches a profile only after finding a literal alias in an eligible block. A regression checks 601 aliases and the profile lookup count. This bounds repeated local work; real catalog latency has not been benchmarked.

## Coverage and verification

The current combined focused remediation suite passes **189 tests**, including extraction checks that a plausible paraphrase and an unrelated same-message name both leave no entity association. It also rejects missing quotes, quotes that omit the name, and references to another message. A JEV source-only alias makes no provider call. The cached-model smoke test collects, but real model artifacts were not run locally. A package warning about `requests` dependencies appeared; the test exit code was 0.

Next high value tests: evaluate real source-only examples before reintroducing automatic paraphrase linking, and test VP-02 with valid handles/blocks but prose that does not support its asserted relation. The latter documents the current model trust boundary before deciding whether to reject it or hold it for review. Benchmark alias count x gap-block count to validate the new preparation cap under a large real catalog.
