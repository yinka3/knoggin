# Source Provenance and Encounter Implementation Plan

**Status:** Proposed design — no implementation in this document  
**Purpose:** Let Knoggin retain traceable evidence for sources the user or an
agent actually encounters, without treating every source as a chat message or
automatically turning source text into user memory.

---

## 1. Product Objective

The capability is not primarily “document ingestion.” Its useful outcome is:

> Knoggin can show what source passage it encountered, where that passage came
> from, and why an observation or future answer is grounded in it.

This should work for:

- a text-based PDF or DOCX that the user has made available to a project;
- a passage returned by `search_documents` or `read_document`;
- a web-search result the agent has seen;
- a web page the agent later opens and reads; and
- a quote, file, or URL supplied by the user.

It must distinguish a source itself from an attribution *about* a source. A
user saying “page 14 of the report says revenue rose 18%” is useful context,
but it is not verified evidence until Knoggin reads that page or the user
supplies the quoted text.

### 1.1 The evidence chain

```text
durable source
  → captured revision
    → exact, located segment
      → encounter by user/agent/system
        → observation or answer evidence
```

For example:

```text
Acme_Q2_Report.pdf
  → SHA-256 revision 8e4…
    → page 14, “Financial Results”, sentences 3–4
      → agent read it via search_documents during run r_123
        → answer says revenue rose 18%
```

The exact segment, not a model summary or an encoded ID, is the evidence.

## 2. Scope and Deliberate Boundaries

### 2.1 First release

The first release should create a durable provenance ledger for sources that
the system actually touches. It should:

1. Preserve page/section/paragraph-aware text for managed, text-based PDFs and
   DOCX files during document indexing.
2. Record source encounters generated by existing document tools:
   `search_documents` and `read_document`.
3. Record web-search results as **discovery evidence** only, including query,
   provider, result URL, title, and exact returned snippet.
4. Add an explicit future “open/read web page” capability before treating a web
   page as directly read evidence.
5. Persist evidence status so callers can tell verified excerpts from user
   claims and provider snippets.
6. Expose the resulting IDs and locators to a later UI/API/SDK. This release
   does not require that public surface to exist yet.

### 2.2 Explicit non-goals for the first release

- No webhook ingestion.
- No automatic model extraction over every uploaded document.
- No automatic creation, invalidation, or profile refinement of active facts
  from a document or web source.
- No fake rows in `messages`, Redis conversation history, or message search.
- No attempt to replace the existing chat pipeline in the same change.
- No claim that a provider search snippet verifies a page’s full content.
- No OCR or image-only document support; this plan begins with text PDFs and
  DOCX only.

This keeps “passive collection” meaningful: the system captures sources and
their provenance when they are encountered, but it does not silently promote
unreviewed external material into personal memory.

### 2.3 Later decisions, not prerequisites

The following should be decided after the ledger is useful in real agent runs:

- which source observations are eligible to become facts;
- whether a user must approve source-derived memory;
- web-content retention length and robots/licensing policy;
- a generic source-aware extraction pipeline; and
- webhook and third-party connector support.

## 3. Evidence Levels

Every encounter needs an explicit evidence level. This is the main protection
against false provenance.

| Level | Meaning | Example | May support a fact automatically? |
|---|---|---|---|
| `primary_excerpt` | Knoggin captured the source text and exact locator | PDF page 14, sentences 3–4 | Not in v1; potentially after policy review |
| `retrieved_excerpt` | A managed-source tool returned the exact stored passage | `read_document` lines/segments | Not in v1; potentially after policy review |
| `discovery_snippet` | Search provider returned a snippet; underlying page was not opened | DuckDuckGo result excerpt | No |
| `user_quote` | User pasted a quotation but source has not been independently checked | User copies a paragraph from a book | No by default |
| `user_reference` | User identifies a source/location without supplying text | “See chapter 3, page 42” | No |
| `agent_summary` | A model’s restatement of an encounter | “The report says…” | Never as sole evidence |

`primary_excerpt` means “we possess this exact captured text,” not “the claim is
universally true.” The source may be stale, speculative, or wrong; provenance
and truth remain separate concerns.

## 4. Current-Codebase Assessment

The relevant foundations already exist, but they are retrieval- and
message-oriented rather than provenance-oriented.

| Current area | What exists today | Gap this plan addresses |
|---|---|---|
| `core/knowledge/documents/service.py` | Durable upload, indexing status, recovery, visibility, document reading, and vector search | Indexing reduces PDF/DOCX content to plain text and RAG chunks; it retains no page/heading/sentence locator |
| `core/knowledge/documents/storage.py` | `pypdf`, `docx2txt`, and `SentenceSplitter` extraction/chunking | PDF pages are joined into one string; DOCX structure is flattened; RAG chunks have no source-span mapping |
| `project_documents`, `document_content`, `document_chunks` | Raw file bytes, content hash, project/session visibility, vector chunks | `document_chunks` only has chunk index, text, and embedding; it cannot prove which page/section produced a chunk |
| `SearchTools.search_documents` / `read_document` | Existing agent access to document results and bounded line reads | Returned content does not receive a durable encounter record or stable source-segment ID |
| `SearchTools.web_search` / `news_search` | Providers return title, URL, and snippet | The system has no record of the query/results, and does not open a source page |
| `AgentExecutor._execute_tools` | Runs tools sequentially then invokes `apply_tool_result_hooks` | A single, appropriate integration seam exists for passive capture, but no provenance hook is registered |
| `IngestionPipeline` and graph writes | Existing chat entity/relationship extraction and evidence persistence | Assumes integer `msg_id` throughout; it must not be reused with fabricated message IDs |
| `facts`, `relationship_evidence_refs`, profile refinement | Durable chat-grounded facts and relationships | Fact and relationship provenance currently reference message IDs only |

### 4.1 Why the older generic-source proposal is too broad for this first step

`DOCUMENT_SOURCE_INTEGRATION.md` proposes a complete `source_events` migration
for messages, documents, and webhooks. The current implementation shows that
this is a larger migration than the proposal implies:

- `messages.message_id`, `EntityRecord`/`ConnectionRecord`,
  `ExtractionTrace`, candidate suggestions, and relationship extraction use
  integer message IDs.
- `write_graph_db.py` converts `msg_*` IDs into the message-only
  `relationship_evidence_refs` table.
- `facts.source_msg_id` and `FactResolver` reject ungrounded or unknown message
  IDs; profile refinement also orders and checkpoints by message ID.
- Message search, dead-letter replay, session context, and profile jobs all
  intentionally operate on conversation history.

Replacing that vocabulary now would combine a provenance feature with a
high-risk memory-pipeline migration. The plan below adds source provenance
alongside chat provenance first. It leaves the chat path intact and gives a
future generic pipeline real source data to build on.

## 5. Target Data Model

Use four new concepts. “Source” is a durable identity; “encounter” is one
specific observation of it by the user or agent.

```text
source_record (the report or canonical web URL)
  └── source_revision (the exact captured version)
        └── source_segment (one locatable sentence / sentence-like unit)
              └── source_encounter (agent or user actually saw it)
                    └── source_observation (later, optional extraction output)
```

### 5.1 `source_records`

One row describes a durable logical source. For a managed document, it links to
the existing `project_documents.document_id`; for a web source, it stores a
canonical URL.

Required fields:

```text
source_id UUID primary key
project_id TEXT not null
kind TEXT not null
  managed_document | web_page | web_search_result | user_reference
document_id UUID nullable → project_documents(document_id)
canonical_url TEXT nullable
title TEXT nullable
source_system TEXT nullable            # document_service, DuckDuckGo, etc.
created_at / updated_at
metadata JSONB not null default {}
```

Constraints:

- A `managed_document` source has `document_id`; its project must match the
  document’s project.
- A `web_page` source has a normalized canonical URL.
- Do not use a polymorphic text reference as the only join mechanism.
- Use a unique index for a document source per document and a normalized URL
  identity per project. Content versions belong in revisions, not in the source
  identity.

### 5.2 `source_revisions`

One source can change. A revision preserves the text version from which an
excerpt came.

```text
revision_id UUID primary key
source_id UUID not null → source_records(source_id)
content_hash TEXT not null
captured_at TIMESTAMPTZ not null
content_mode TEXT not null             # document_text | bounded_web_excerpt | search_snippet
mime_type TEXT nullable
retrieval_metadata JSONB not null      # HTTP/content headers, page count, etc.
```

For a managed document, `content_hash` should agree with
`project_documents.content_hash`. For web pages, a changed normalized body
creates a new revision even when the canonical URL is the same.

Do not store an unlimited raw web page by default. A later web-reader should
store the exact bounded excerpt(s) it returned, their hash, and relevant HTTP
metadata. Full-page archival is a separate retention and policy decision.

### 5.3 `source_segments`

A source segment is the smallest persistent evidence unit. In the document
case it is normally a full sentence; headings, bullets, and table rows may be
sentence-like units.

```text
segment_id UUID primary key
revision_id UUID not null → source_revisions(revision_id)
ordinal INTEGER not null
content TEXT not null
content_hash TEXT not null
locator JSONB not null
char_start INTEGER nullable
char_end INTEGER nullable
UNIQUE(revision_id, ordinal)
```

Typical `locator` values:

```json
// PDF
{"kind":"pdf","page":14,"section_path":["Financial Results"],
 "page_char_start":92,"page_char_end":171}

// DOCX
{"kind":"docx","paragraph":37,"section_path":["Results","Revenue"],
 "paragraph_char_start":0,"paragraph_char_end":79}

// Web page
{"kind":"web","url":"https://example.com/report","heading_path":["Q2 Results"],
 "excerpt_char_start":0,"excerpt_char_end":135}

// Search provider snippet
{"kind":"search_result","provider":"duckduckgo","query":"Acme Q2 revenue",
 "rank":2,"result_url":"https://example.com/report"}
```

Locations must be structured data, not only a display string. The UI can render
“page 14 · Financial Results,” while the SDK can retrieve an exact segment ID.

### 5.4 `source_encounters`

This is the passive ledger. It records that the system or user actually saw a
source segment; it is not itself a fact.

```text
encounter_id UUID primary key
project_id TEXT not null
session_id TEXT nullable
actor_kind TEXT not null               # agent | user | system
encounter_kind TEXT not null
  document_search | document_read | web_search | web_read | user_quote | user_reference
evidence_level TEXT not null
tool_name TEXT nullable
agent_run_id TEXT nullable
idempotency_key TEXT nullable unique
observed_at TIMESTAMPTZ not null
metadata JSONB not null default {}
```

Because one action may return several passages, use a child
`source_encounter_segments` table rather than forcing one segment per
encounter:

```text
encounter_id UUID → source_encounters
segment_id UUID → source_segments
position INTEGER not null
PRIMARY KEY (encounter_id, segment_id)
```

`idempotency_key` must be derived from the agent run ID, tool-call ID, and
result position. The current tool hook receives only tool name/result, so its
signature must also receive the `ToolCall` or `call_id` from
`AgentExecutor._execute_tools`.

### 5.5 Future-only observation and evidence tables

When source extraction is deliberately enabled, add:

```text
source_observations
  observation_id, encounter_id, kind, payload, status,
  extractor_version, created_at

source_observation_evidence
  observation_id, segment_id, quote_start, quote_end
```

Use `candidate`, `accepted`, and `rejected` observation status. Do **not** add
an unstructured `source_event_id` column to every existing table as the first
change. When the product has a source-to-fact policy, add explicit many-to-many
fact/relationship evidence tables so a claim can have more than one source and
chat evidence remains intact.

## 6. Document Provenance Design

### 6.1 Preserve structure before it is flattened

Today `extract_text()` does this for PDFs:

```text
page 1 text + page 2 text + … → one string
```

That is sufficient for current RAG indexing but discards the page boundary that
the user needs for a trustworthy reference. DOCX extraction similarly uses
`docx2txt`, which loses paragraph and heading structure.

Add a structured extraction result alongside the existing plain-text helper:

```text
ExtractedDocument
  blocks[]
    kind: heading | paragraph | bullet | table_row
    text
    locator: page / paragraph / section path
```

- **PDF:** iterate `PdfReader.pages` independently and retain the one-based
  PDF page number. Build blocks from each page’s extracted text. A page is a
  reliable locator even if visual layout is imperfect.
- **DOCX:** use a structure-preserving reader (likely `python-docx`, which is
  not currently a dependency) to retain paragraphs and heading levels. Keep
  `docx2txt` only if needed for compatibility, not for provenance extraction.
- **No OCR in v1:** reject or mark image-only PDFs as not provenance-ready
  rather than inventing page text.

`extract_text()` can remain as a compatibility adapter that joins structured
blocks for existing callers. The provenance path must consume the structured
form directly.

### 6.2 Sentence-first segments and windows

RAG chunks and evidence segments have different jobs:

```text
Structured document blocks
  → complete sentence segments (durable evidence)
    → overlapping sentence windows (model input / future extraction)
      → larger RAG chunks (semantic retrieval)
```

Rules for source segments:

1. Segment each block into full sentences using a dedicated, deterministic
   sentencizer. Reuse the configured spaCy capability only through an explicit
   injected service; do not duplicate a hidden, separately configured NLP
   model in `DocumentService`.
2. Preserve headings, bullets, and table rows as sentence-like units when
   ordinary sentence splitting is unsuitable.
3. Store an ordinal plus block-local and page/paragraph character offsets.
4. Never join a sentence across PDF pages or DOCX paragraphs merely to meet a
   token limit.
5. For an unusually long sentence, retain the original sentence segment and
   create bounded display/model subspans with a documented split reason.

Future extraction should receive windows of roughly 150–250 tokens made of
complete sentences, with one or two sentences of overlap. The durable evidence
must point to the individual sentence segments, not only the window.

### 6.3 Keep RAG and evidence indexing separate but linked

The existing `SentenceSplitter(chunk_size=512, chunk_overlap=50)` produces
RAG-oriented chunks. It should remain a retrieval concern, not become the
authoritative citation unit.

During a document reindex, create a mapping such as:

```text
document_chunks                    document_chunk_source_segments
--------------                     ------------------------------
chunk_id                           chunk_id
document_id                        segment_id
chunk_index                        position
content                            quoted_char_start/end (optional)
embedding
```

This mapping is required. Without it, a `search_documents` result can only say
“chunk 8,” not “page 14, Financial Results, sentences 3–4.”

Build retrieval chunks from contiguous canonical sentence segments, or return
explicit source-span data from the chunker. Do not attempt to recover source
locations later with a naïve `text.find()`; repeated boilerplate and overlap
make that ambiguous.

### 6.4 Existing documents and document updates

- New documents receive structured segments on their next indexing pass.
- Existing `indexed` documents must enter a distinct `provenance_pending`
  state or be selected by a separate recovery query; do not silently mark them
  unindexed or block their existing RAG availability.
- Provenance preparation is idempotent on document ID plus content hash.
- A changed document content hash creates a new source revision and fresh
  segments. Existing encounters continue to point to the old revision.
- Deleting a project document should follow the project’s existing cascade and
  retention rules. Decide explicitly whether evidence is deleted with private
  source material or retained only as a redacted tombstone; default to cascade
  deletion for the project-owned, user-deleted source.

## 7. Agent and User Encounter Capture

### 7.1 Existing document tools

The existing agent tool paths are the first capture adapters:

| Tool | Current result | Capture behavior after this change |
|---|---|---|
| `search_documents` | RAG chunks plus document metadata and score | Create one `document_search` encounter for the returned chunks, linked through the chunk-to-segment map; mark `retrieved_excerpt` |
| `read_document` | Re-extracted numbered plain-text lines | Return stable source-segment IDs and locators, then create a `document_read` encounter for the selected segments |
| `get_document_info` / listings | Metadata only | Do not create an evidence encounter; metadata inspection is not source-text reading |

The user-facing text result should include a compact citation payload, for
example:

```json
{
  "content": "…revenue increased 18%…",
  "source": {
    "source_id": "…",
    "revision_id": "…",
    "segment_ids": ["…", "…"],
    "display_locator": "Acme Q2 Report.pdf · p. 14 · Financial Results"
  }
}
```

The agent sees the citation context in its tool result, which makes grounded
answers possible without asking the model to reconstruct location metadata.

### 7.2 Web search and page reading

Current `web_search` and `news_search` only call search providers. They return
title, URL, and snippet; neither tool fetches the URL.

Therefore:

1. Capture a successful result as `web_search` with
   `evidence_level=discovery_snippet`.
2. Store the provider-returned snippet exactly, along with query, rank,
   provider, title, URL, and retrieval time.
3. Never label the result as a verified webpage excerpt.
4. Add a separate `read_web_page`/`open_web_source` tool before the agent may
   claim to have read the page. That tool needs URL validation, SSRF protection,
   redirect limits, content-type and byte limits, HTML-to-text normalization,
   heading/anchor extraction, and a retention policy.
5. The new reader returns a bounded, numbered/located excerpt and records a
   `web_read` encounter at `primary_excerpt` or `retrieved_excerpt` level.

A web result may be useful to an agent immediately, but the system should
describe it as “a search-result snippet indicated…” until the page is opened.

### 7.3 User-supplied references

No background LLM should attempt to resolve every book title or page reference
in chat. Capture only explicit source-bearing inputs:

- uploaded file → managed document source;
- pasted quotation → `user_quote` segment;
- URL supplied by user → `user_reference`, upgraded only after successful read;
- optional structured citation supplied by a future UI → `user_reference` with
  book/report/page metadata.

An ordinary conversation message remains governed by the current message
pipeline. A user’s unsupported statement should not gain a `primary_excerpt`
badge just because it contains a title and page number.

### 7.4 The correct capture seam

`AgentExecutor._execute_tools` already executes a tool and calls
`apply_tool_result_hooks(ctx, tools, tool_name, result)`. Add a provenance hook
there rather than scattering writes throughout every search provider.

Required adjustments:

1. Pass the `ToolCall` (at minimum its `call_id` and arguments) into the hook.
2. Register one `SourceEncounterRecorder` on the project/runtime and make it
   available through `Tools` or the execution context.
3. Let the hook recognize only capture-eligible successful tools.
4. Persist the small source/encounter transaction before discarding the tool
   result. A capture failure should be logged and metered but should not turn a
   successful user-facing read/search into an agent failure.
5. Never capture error placeholders such as “No Results,” provider errors, or
   tool authorization failures as sources.

This preserves a single audit point for agent accesses and works for newly
added search/read tools as long as they return a defined provenance payload.

### 8.1 Existing areas intentionally left unchanged at first

Do not modify these in the first ledger release:

- `messages`, `message_search`, Redis chat queues, or DLQ replay;
- `IngestionPipeline.run(messages, ...)` and the message-ID extraction prompts;
- `ConnectionRecord.msg_id`, `MessageConnections`, or the existing
  `relationship_evidence_refs` schema;
- `facts.source_msg_id`, `FactResolver`, and profile-refinement checkpoints;
- automatic fact auditing or fact correction flows.

The first release records the source evidence that a later source-aware
extraction or fact-promotion path will need. It should not simulate that path
with invented message IDs.

## 9. Future Source-Aware Extraction (Separate Phase)

Once encounters are valuable and the promotion policy is decided, generalize
extraction deliberately. The target input should be a typed source input, not a
dictionary shaped like a message:

```text
SourceExtractionInput
  source_id
  revision_id
  segment_ids
  content_window
  evidence_level
  project_id
  session_id (optional process context)
  encountered_at
```

The extraction result must return source IDs/segment IDs rather than `msg_id`.
Chat should become one adapter that constructs a source input from a message;
it should not be deleted first.

### 9.1 Required migration work when this phase begins

1. Introduce source-oriented contracts alongside `ConnectionRecord`,
   `MessageConnections`, `CandidateSuggestion`, `ExtractionTrace`, and
   `BatchResult`.
2. Update prompts and validators to emit a source/segment reference and prove
   that every relationship observation is supported by the returned source
   segment.
3. Add new relationship-source evidence storage rather than overloading the
   message-only `relationship_evidence_refs` primary key.
4. Add fact evidence links that can reference multiple message and non-message
   sources. Keep the current message fields during migration.
5. Separate conversational profile synthesis from external-source observations.
   Documents are often historical, hypothetical, or third-party statements;
   they should not automatically alter a user profile.
6. Backfill or adapt message evidence only after the new path has contract and
   integration coverage.

### 9.2 Promotion policy before active fact writes

The source-to-fact policy needs product decisions, for example:

```text
source observation
  → candidate memory with citation
    → user approval or high-trust policy
      → active fact with one or more evidence links
```

At minimum, a fact derived from an external source should record:

- its supporting segment IDs and quoted spans;
- evidence level and source kind;
- extraction/model version;
- actor/policy that promoted it; and
- a way to show the original passage in the UI/SDK.

This is compatible with the new forward-correction fact audit work, but it is
not part of the initial provenance ledger.

## 10. Delivery Sequence

### Phase 0 — confirm contracts and policy

Write the final schemas, source kinds, evidence-level enum, retention default,
and what counts as a source encounter. Confirm that uploaded project documents
may be retained as evidence according to the project’s existing privacy model.

**Exit condition:** one written contract covers document search/read, web
search snippets, user quotations, and user references.

### Phase 1 — provenance storage and structured document indexing

1. Add the source/revision/segment/encounter tables and storage boundaries.
2. Build structured PDF and DOCX extraction.
3. Create sentence segments and retrieval-chunk-to-segment mappings.
4. Make this preparation idempotent and recoverable for existing documents.
5. Keep current RAG reads/searches working throughout.

**Exit condition:** a text PDF’s retrieved chunk can be traced deterministically
to document ID, content hash, PDF page, and exact sentence IDs.

### Phase 2 — passive capture from existing agent tools

1. Pass `ToolCall` information to tool-result hooks.
2. Add `SourceEncounterRecorder` and one capture hook.
3. Capture successful document reads/searches and web/news-search snippets.
4. Add citation payloads to relevant tool results.
5. Add an inspection method in the core service/SDK-facing layer; a UI/API
   endpoint can consume it later.

**Exit condition:** an agent run can list exactly which document passages and
search snippets it used, without creating any message rows or facts.

### Phase 3 — explicit web-page reader

1. Define URL and network safety policy.
2. Implement bounded fetch, readable-text extraction, heading locator, and
   response-size/time limits.
3. Record a web source revision and excerpt segments.
4. Capture `web_read` encounters through the same hook.

**Exit condition:** the system distinguishes “search result suggested this”
from “agent read this page section.”

### Phase 4 — source observations and promotion experiment

Implement only after observing Phase 2/3 data and choosing a memory policy.
Start with candidate observations and citations, not fact/profile mutation.

**Exit condition:** an evaluator can reject an unsupported observation and the
system can show its exact source context.

### Phase 5 — generic extraction and optional connectors

Only now consider moving chat and non-chat extraction to a shared source-input
contract, and only later consider webhooks. This phase includes the explicit
message-to-source migration described in section 9.

## 11. End-to-End Behavior Examples

### A. Agent searches an uploaded PDF

**Today**

```text
Agent calls search_documents("Acme revenue")
→ gets RAG chunk 8
→ may answer from that text
→ no durable record says which page/passage was used
```

**After Phase 2**

```text
Agent calls search_documents("Acme revenue")
→ gets chunk 8 + source spans [p.14 sentences 3–7]
→ hook records a document_search encounter for those spans
→ agent can cite “Acme Q2 Report.pdf · p. 14 · Financial Results”
→ no fact or user profile changes merely because the result was read
```

### B. User mentions a page but has not provided the book

**Today**

```text
“Page 42 of the report says the launch is delayed.”
→ ordinary chat text; later systems could mistake it for verified source text
```

**After Phase 2**

```text
→ optional user_reference encounter:
   title/report unknown or supplied, page 42, statement attributed by user
→ evidence_level=user_reference
→ no source revision/verified segment exists
→ UI/SDK can say “not independently verified”
```

### C. Agent performs a web search

**Today**

```text
web_search("Acme Q2 revenue")
→ title, URL, provider snippet
→ result disappears after the run
```

**After Phase 2**

```text
→ each usable result is recorded as a discovery_snippet encounter
→ exact snippet, query, provider, rank, URL, and time are retained
→ agent must not describe this as having read the linked page
```

### D. Agent opens a web page (future Phase 3)

```text
read_web_page("https://example.com/acme-q2")
→ safe bounded fetch and readable-text extraction
→ sections and sentence segments persist as a new web revision
→ selected excerpt receives a web_read / primary_excerpt encounter
→ any later candidate observation can cite the exact heading and text span
```

## 12. Test and Verification Plan

### Unit contracts

- PDF extractor keeps one-based page number and page-local offsets.
- DOCX extractor preserves heading path and paragraph ordinal.
- Sentence segmenter never crosses a block/page boundary.
- Long-sentence fallback preserves a parent sentence and records its split.
- RAG chunk mappings reference only contiguous, visible source segments.
- Document/source revision upserts are idempotent on content hash.
- Encounter idempotency prevents a hook retry from duplicating one tool result.
- Provider error/no-result payloads cannot create encounters.
- A search snippet receives `discovery_snippet`, never `primary_excerpt`.

### Storage integration contracts

- Project/session visibility prevents one project from reading another project’s
  source, segment, or encounter data.
- Deleting a document follows the selected cascade/tombstone policy.
- Reindexing an unchanged document does not duplicate source segments.
- Updating content creates a new revision and preserves past encounter links.
- Existing indexed documents remain searchable while provenance backfill runs.

### Agent integration contracts

- `search_documents` records the exact returned segment IDs.
- `read_document` records only the selected line/segment range.
- `web_search` captures provider data with run/tool-call idempotency.
- Tool result capture failure is visible in metrics/logs but does not transform a
  successful read/search into an agent error.
- The agent can receive a compact citation payload and cite it without guessing
  a page number.

### Manual acceptance scenarios

1. Upload a multi-page PDF, ask about a sentence on page 14, then inspect the
   encounter and confirm it points to page 14 and the original sentence.
2. Upload a DOCX with nested headings; verify a returned segment includes its
   paragraph and heading path.
3. Search the web but do not open a result; confirm the system labels it as a
   snippet/discovery source.
4. Open a page through the future reader; confirm the source record includes
   the retrieved text, locator, capture time, and URL.
5. Mention a book page in chat without a quote; confirm it remains an
   unverified reference rather than a verified source.

## 13. Risks and Decisions to Make Before Implementation

| Risk / question | Recommended decision |
|---|---|
| PDF extracted text can be visually imperfect | Promise page-level provenance, not pixel-perfect citation; retain exact extracted text used by the agent |
| DOCX “page number” varies by renderer | Cite heading + paragraph ordinal; do not manufacture page numbers |
| Duplicate sentence text | Use revision ID + ordinal + offsets, never text equality alone |
| Document reindex cost | Prepare provenance alongside future indexes and recover in bounded background batches |
| Search snippets can be wrong/stale | Make `discovery_snippet` visually and semantically distinct from read evidence |
| Web fetching security | Ship no page reader until SSRF, redirect, MIME, timeout, and size controls are designed and tested |
| Web content retention | Default to bounded evidence excerpts; decide full-page archival separately |
| Memory pollution | Capture encounters first; require an explicit source-observation and promotion policy before fact writes |
| Scope expansion | Defer webhooks and message-pipeline generalization until the ledger proves useful |

## 14. Recommended First Implementation Slice

The smallest complete slice is:

1. **Text PDF only**: create structured page/sentence segments and map RAG
   chunks to them.
2. **Existing document tools only**: record `search_documents` and
   `read_document` encounters through the executor hook.
3. **Inspection only**: provide source/encounter reads in the core service,
   without a UI/API requirement and without fact writes.

This proves the central user value—“show me exactly where the agent got this”
—with the least disruption. DOCX structure, web-search snippet capture, and a
web-page reader can then be added one at a time using the same data model.

The first slice should be considered successful only if a retrieved PDF passage
can be traced from an agent run back to the correct uploaded document, content
revision, PDF page, and exact stored sentence text.
